# ADR-005: Sign-in Methods, Email Delivery and Account Linking

## Status

Accepted.

## Context

Authentication was email and password only, with no email delivery anywhere in the monorepo. Adding a second factor, passkeys, OAuth and single sign-on on top of that raises three questions this ADR settles: which methods may open an account on their own, how mail leaves the box, and which of those methods open the _same_ account.

There was no way to send anything, and two flows cannot exist without one: confirming that whoever typed an address can read it, and resetting a password nobody remembers. A self-hosted instance cannot be assumed to have any particular transport — an operator may hold a Resend key, an SMTP relay inside their network, or neither while they are still developing. `CONTEXT.md` already settles what to do with a dependency like that: "providers are interchangeable connectors, never the core of the application", and `packages/api/src/providers/` implements exactly that shape for banking, where Enable Banking is one adapter behind a boundary rather than a dependency of the project.

And once a deployment can offer more than one door — a password, a passkey, Google, Apple, an organisation's OpenID Connect provider — the question becomes which of those doors open the same account. Getting that wrong is not a usability defect, it is an account-takeover path: an attacker who registers an unverified account at a victim's address and then waits for the victim to sign in with Google has the victim's identity linked into an account the attacker controls the password for.

## Decision

### 1. A password is always the first factor; sign-in by emailed code is refused

Every account that signs in with an address signs in with a password. `emailAndPassword.enabled` is `true` unconditionally — there is no variable that turns it off — with `minPasswordLength: MIN_PASSWORD_LENGTH` (12).

An earlier iteration of this work made a six-digit code emailed to the address the primary way in. It was rejected, because it makes the mailbox the account's floor: two-factor authentication would then guard the password while an emailed code opened the same door beside it, so the second factor buys nothing a mailbox compromise does not undo — and an account created that way holds no `credential` row, so it cannot enrol a second factor at all. A method that lowers every account to the strength of its mail provider is not worth the convenience.

`emailOTP` therefore stays registered — for address confirmation and password reset, and nothing else — while the passwordless route registering it also exposes is refused outright. `DISABLED_PATHS` names `/sign-in/email-otp`, and `enforceAuthPolicy` (`hooks.before`) answers it `404 NOT_FOUND`. A plugin that brings an endpoint this deployment does not offer is refused at the router rather than left reachable because it happened to come in the box.

Closing that one route is not enough, and both remaining gaps were real. `/email-otp/send-verification-otp` stayed open to anyone, so a caller could ask for a code of type `sign-in` and Freenary would mail "Your Freenary sign-in code" to whatever address it named — for a code nothing would accept. That is an unauthenticated mailer and a phishing lure written in the product's own words. `OTP_ISSUING_PATH` and `DISABLED_OTP_TYPES` refuse that purpose at the same hook with `400` / `INVALID_OTP_TYPE`, and `emails.ts` has no `sign-in` arm left, so the copy cannot be composed even if some other route reached the sender.

And confirmation itself signed people in a second time. `autoSignInAfterVerification` is deliberately on — it is what lets sign-up finish in one step — but `/email-otp/verify-email` neither checks nor changes anything for an address that is already confirmed, so a code emailed to an existing account minted a session past the password and past the second factor: exactly the door this decision refuses. `emailVerification.beforeEmailVerification` now rejects a confirmation whose user is already `emailVerified`, with `400` / `INVALID_OTP`. That guard carries as much of this decision as the refused route does — a passwordless sign-in existed here without any sign-in endpoint being reachable. Turning `autoSignInAfterVerification` off would close it too, at the cost of making every new account sign in again immediately after typing the code; the guard keeps the one-step sign-up and refuses only the case that has no legitimate meaning. Neither flag may be flipped without re-opening this paragraph.

The cost is an account-existence oracle. The sign-in form is progressive: the reader types an address, and the form reveals a password for an account that exists or a name and a password for one that does not. It gets that answer from `auth.accountExists`, a public procedure, so anyone who can call it can ask whether an address is registered. That answer cannot be hidden while the form works this way, so it is capped instead: `ACCOUNT_EXISTS_RATE_LIMIT` allows 20 calls per 60 seconds per caller — per caller only where the caller can be identified, which is what `TRUSTED_PROXIES` is for, in the consequences below. **The cap is the mitigation, not a fix** — it makes enumerating a list cost more than it is worth; it does not make a single lookup private.

The reveal step is the whole of the oracle. Sign-**up** still answers identically for a taken address and a free one, because `requireEmailVerification` withholds the session either way — both responses say a code is waiting, neither is a session. That holds wherever email is configured; decision 3 records what it costs when none is.

Rejected alternatives:

- **Keeping the emailed code as a second way in, next to the password.** The floor argument above. An account is only as strong as its weakest door, and this one is a mailbox the project does not control.
- **Asking for a password before knowing whether the address has an account.** One form for both cases either shows a name field to everybody or collects it after the fact, and it collapses "wrong password" and "no such account" into the same dead end. The oracle is the price of telling the reader which of the two they are in.
- **Hiding the existence answer.** There is nowhere to hide it: the form needs it before anyone has authenticated. Raising the cost further — a proof-of-work or a CAPTCHA on the reveal — stays a deployment concern rather than a dependency this project ships.

### 2. A passkey is a primary sign-in method, not a second factor

`@better-auth/passkey` is registered unconditionally, with the `Passkey` table behind it, and a registered passkey signs its holder in on its own. It sits below the divider with Google, Apple and single sign-on, not in the second-factor step.

That placement is what the two plugins actually implement, not a preference. Better Auth's `twoFactor` plugin matches exactly `/sign-in/email`, `/sign-in/username` and `/sign-in/phone-number` — it can only interpose on a password sign-in. And `@better-auth/passkey`'s `/passkey/verify-authentication` creates a session and sets the session cookie itself; there is no endpoint that verifies a passkey as the second half of somebody else's sign-in. So a passkey is a first factor by construction: two-factor guards the password, and a passkey stands beside it.

The relying party is the **web app's own origin**, taken from `CORS_ORIGIN`, not the API's — its hostname as the relying-party id, and the whole origin as the origin the server expects back:

```ts
const webOrigin = new URL(env.CORS_ORIGIN);
passkey({
  origin: env.CORS_ORIGIN,
  rpID: webOrigin.hostname,
  rpName: APP_NAME,
});
```

WebAuthn binds a credential to the origin that created it, and the ceremony runs in the browser — on the web app's origin, which is a different hostname from the API in any split deployment. Two consequences follow and are accepted deliberately: a credential registered against one deployment cannot be replayed against another, and **changing `CORS_ORIGIN` invalidates every registered passkey, the port included**. `rpID` is only the hostname, so a browser will still offer a credential after a port change; but the plugin forwards `origin` to SimpleWebAuthn as `expectedOrigin`, and `verifyAuthenticationResponse` compares it to the origin in the signed `clientDataJSON` by exact string — scheme, host and port. Moving `https://app.example.com` to `https://app.example.com:8443` therefore refuses every existing credential at verification time. There is no variable for the relying party, because a value an operator could set independently of the origin the browser reports is a value that can only be set wrong.

Rejected alternatives:

- **A passkey as the second factor after the password.** No endpoint implements it, and writing one would mean re-implementing the plugin's ceremony to withhold the session it already grants.
- **Its own `AUTH_PASSKEY_RP_ID` variable.** WebAuthn refuses a relying-party id that does not match the calling origin, so the only correct value is the one already derivable from `CORS_ORIGIN`. A settable one adds a way to break sign-in and no way to fix it.
- **Registering the plugin only when something is configured.** Nothing is configured: passkeys need no credentials and no third party, so `authCapabilities.passkey` is `true` on every deployment. Whether the reader's browser can use them is a client fact — WebAuthn needs a secure context — and the interface reads it from the browser rather than from the server.

### 3. Email is a provider boundary, resolved once at import

Email is needed for two flows: confirming an address after sign-up, and resetting a forgotten password. It is not what sign-in runs on.

`packages/email` mirrors the banking connector boundary. `types.ts` declares `EmailProvider` — a `readonly id` and `send(message)` — and `EmailMessage`, which carries `to`, `subject` and plain-text `text` only, because every message this application sends is a short transactional notice. Three adapters implement it:

- **`resend`** talks to `https://api.resend.com/emails` with one `fetch`. No vendor SDK: a single POST covers the whole surface used here, and nothing ships to production for it.
- **`smtp`** uses nodemailer with `pool: true`, so one transport serves the process and a message does not pay for a fresh TCP and TLS handshake — nodemailer pools nothing without that flag. The port defaults to 465 when `SMTP_SECURE` is on and 587 otherwise, and authentication is omitted entirely when `SMTP_USER` is unset, so a relay that authenticates by network position works.
- **`log`** prints the message, one-time code included, to the server log with `console.info` and delivers nothing.

`registry.ts` owns the choice. `createEmailProvider` takes an explicit `EmailSettings` — so the resolution rules are testable without touching the environment — and the module builds `emailProvider` from `@freenary/env/server` once, at import. Everything above it consumes `isEmailEnabled` and `sendEmail` from `packages/email`; no caller names a transport.

**Codes, not links.** `overrideDefaultEmailVerification: true` puts address confirmation on the same six-digit codes as password reset. A link is pre-fetched by mail clients and breaks when the mail is read on a different device from the one the flow started on; a code the reader types works from anywhere, and it leaves one delivery path to keep working instead of two.

**Misconfiguration throws at import, not at delivery.** A provider named but left half-configured — `EMAIL_PROVIDER=resend` with no `RESEND_API_KEY`, `smtp` with no `SMTP_HOST`, either with no `EMAIL_FROM` — fails while the process is starting, with the missing variable in the message. The alternative is a server that boots, accepts a sign-up, and swallows the code: the operator sees a healthy process and the _user_ is the one who discovers the breakage, from a screen that only ever says "check your inbox".

**`log` is refused when `NODE_ENV=production`.** It is a development convenience that writes credentials to a log file, and it is indistinguishable from a working transport unless someone reads the log. Refusing it at startup is the only point where that mistake is still cheap.

Rejected alternatives:

- **A vendor SDK per provider.** Resend's SDK adds a dependency to serve one POST, and each further transport would add another. The interface is small enough that `fetch` and nodemailer cover it.
- **Sending mail from `packages/auth`.** It would couple the authentication configuration to a transport, put HTTP and SMTP concerns in the package that owns security policy, and give any future non-auth message nowhere to live. `packages/auth/src/emails.ts` owns the _copy_ and calls `sendEmail`; it knows nothing about how the message leaves the box.
- **A no-op fallback when no provider is configured.** Silently discarding mail is the failure above, made permanent. Instead `emailProvider` is `null`, `isEmailEnabled` is `false`, and the flows that cannot work without a transport are not offered: the `emailOTP` plugin is not registered, `requireEmailVerification` is off, and `authCapabilities.emailDelivery` is `false` so the form shows no "forgot password" link. `sendEmail` still throws if something calls it anyway. The honest cost of that state is in the consequences below.

### 4. One person, one account — implicit linking only between two verified addresses

`account.accountLinking` is `enabled: true` with `allowDifferentEmails: false` and `allowUnlinkingAll: false`. A user who signed up with a password and later arrives through Google lands in the same account, provided both of these hold:

- the identity provider reports the address as verified, and
- the local `user` row is already `emailVerified`.

The second condition is what closes the pre-registration attack. Without it, an unverified row created at a victim's address is a container waiting for the victim's OAuth identity to be linked into it. Better Auth's defaults happen to agree — no provider is listed in `trustedProviders`, and `requireLocalEmailVerified` defaults to `true` — so this is a decision recorded, not a flag flipped: nothing may add a trusted provider without re-opening it.

`allowDifferentEmails: false` keeps the join key the address; `allowUnlinkingAll: false` means the last remaining sign-in method cannot be removed, so an account can never be left with no door.

### 5. Changing which identities open the account needs a session under 15 minutes old

`REAUTH_PATHS` names `/link-social`, `/unlink-account`, `/passkey/delete-passkey` and both halves of passkey registration, and `enforceAuthPolicy` — the one `hooks.before` middleware, which also serves decision 1 — rejects both unless the current session was created within `REAUTH_WINDOW_SECONDS` (900). No session is `401 UNAUTHORIZED`; a stale one is `403` with `code: "SESSION_NOT_FRESH"`, which the interface recognises and turns into "sign in again", not a generic failure.

That check exists because Better Auth guards the two endpoints unevenly: `/unlink-account` is behind `freshSessionMiddleware`, `/link-social` behind the plain `sessionMiddleware`. Both change which credentials open the account, so an attacker on a borrowed laptop needs only the weaker of the two to add their own identity — linking is the more dangerous half, and it was the unguarded one.

Lowering `session.freshAge` to the same fifteen minutes was rejected, and that rejection was only half an answer. `/list-sessions` is behind the same `freshSessionMiddleware`, so a fifteen-minute `freshAge` would make the active-sessions screen — the screen someone opens _because_ they suspect a problem — fail for anyone signed in longer than that. That much holds. What it missed is that leaving `freshAge` at its **24-hour default** broke the same screen anyway: freshness is measured from the session's `createdAt`, which never moves, and a session lasts seven days, so from its second day onward the endpoint the argument existed to protect answered `403`.

So the setting is not left alone, it is raised. `SESSION_EXPIRY_SECONDS` (7 days) is both `session.expiresIn` and `session.freshAge`, which makes Better Auth's fresh gate pass for the whole life of a session and leaves the narrow window entirely to the hook, on the two endpoints that asked for it. A gate keyed on `createdAt` cannot express "authenticated recently" for a long-lived session at all — it only ever answers "signed in recently" — so pushing it out to the lifetime is not weakening it, it is admitting that it never measured what this decision needs. The hook is where that distinction can live.

Raising it has one consequence the hook has to absorb: `freshAge` gates more than the two endpoints above. It also gates `/passkey/generate-register-options` and `/passkey/verify-registration`, because the passkey plugin defaults `registration.requireSession` to true, and `/delete-user`, which this deployment does not enable. Registering a passkey adds a primary way in — one that needs neither the password nor the second factor and survives a password change — so it belongs in `REAUTH_PATHS` for exactly the reason linking does, and it is named there. The rule that follows: `freshAge` is now inert as a protection, so any endpoint that changes which credentials open an account has to be listed in `REAUTH_PATHS` **unless it already demands the account password**, and enabling user deletion means adding it too.

That exception is why the two-factor endpoints are deliberately outside the list. `/two-factor/enable`, `/two-factor/disable` and `/two-factor/generate-backup-codes` all change which credentials open the account, and each one requires the password itself — a stronger proof than a fifteen-minute window, and the reason an account with no password cannot enrol at all. Renaming a passkey is outside the list for the opposite reason: it changes nothing about how the account opens.

### 6. Same-site is decided from evidence: identical hostnames, or a declared parent domain

`resolveCookiePolicy(BETTER_AUTH_URL, CORS_ORIGIN, isProduction, AUTH_COOKIE_DOMAIN)` returns `SameSite=Lax` in exactly two cases and `None` otherwise. The two are identical hostnames, and a declared `AUTH_COOKIE_DOMAIN` — the operator naming the parent domain both origins sit under, which is also what switches on Better Auth's `advanced.crossSubDomainCookies` so the cookie carries `Domain=` and both origins send it.

There is no third, cleverer case, and that is the decision. Browsers judge same-site by registrable domain, and a registrable domain cannot be derived from a hostname: `api.example.co.uk` and `app.example.co.uk` are same-site while a pair that merely shares `co.uk` is not, and telling them apart needs a public-suffix list. Shipping that list — or a "strip one label" heuristic standing in for it — would put the cookie policy on a table that goes stale, and the failure direction is a cookie declared same-site when it is not.

The cost is borne by the deployment that says nothing. A split-subdomain instance with `AUTH_COOKIE_DOMAIN` unset gets `SameSite=None`, so the session, trusted-device and two-factor cookies **are** attached to cross-site requests — a third-party page's `fetch`, `XMLHttpRequest`, form post or subresource — which `Lax` sends on nothing but a top-level navigation. That is why the variable exists and why the operator page tells operators to set it, rather than the server guessing on their behalf. `None` also requires `Secure`, so the one unusable combination — split hostnames, no declared domain, plain HTTP — throws at startup in production and warns in development instead of shipping a sign-in whose cookie the browser drops.

## Consequences

- The minimum password length is `MIN_PASSWORD_LENGTH` (12) with no character-class rule, because length is the only property a rule can enforce that reliably raises guessing cost. `haveIBeenPwned` is registered when `AUTH_PASSWORD_BREACH_CHECK` is on — a SHA-1 prefix leaves the server, so an air-gapped deployment turns it off.
- One-time codes are stored hashed (`storeOTP: "hashed"`), so a database dump contains no code that still opens an account. They are 6 digits, expire after `OTP_EXPIRY_SECONDS` (600), and burn after `OTP_ALLOWED_ATTEMPTS` (3) wrong guesses. Their purposes are address confirmation and password reset: the first confirmation of a new account does hand out a session, which is what makes sign-up one step, and every other use of a code hands out none — a second confirmation and a sign-in code are both refused outright (decision 1), and a reset returns the user to the sign-in form.
- `requireEmailVerification` is what makes sign-up stop being an account-existence oracle: with it on, a taken address and a free one produce the same response, because neither returns a session. It is set to `isEmailEnabled` — demanded only where a code can actually be delivered. A deployment with no email provider therefore hands out a session at sign-up and reveals whether an address is registered by two routes rather than one, and has no password reset at all; that is the honest cost of running without a transport.
- "Remember this device for 30 days" is `TRUSTED_DEVICE_DAYS` (30), passed to the plugin as `trustDeviceMaxAge: TRUSTED_DEVICE_SECONDS`. The interface names the number, so it is set here rather than inherited silently — the plugin's own default is the same 30 days. `trustDevice` rides on both `verifyTotp` and `verifyBackupCode`, and every sign-in inside the window re-issues the trust record, so a device in daily use never sees the second-factor step again while it stays in use.
- The `twoFactor` plugin intercepts password sign-in only — `/sign-in/email` and its username and phone-number siblings — not a passkey ceremony and not the OAuth callback. Enrolment also needs the account password, so an account created through a connected provider cannot enrol two-factor; it can register a passkey, which is why the sidebar's "protect your account" step is satisfied by either one.
- Rate limiting is stored in the database (`RateLimit`), not in memory, so restarting the server cannot clear a lockout, and a multi-process deployment shares one counter instead of one per worker. It is on outside `NODE_ENV=test`, in development too: a limiter that only exists in production is one nobody has ever seen work. `RATE_LIMIT_RULES` caps password sign-in, social sign-in, sign-up, both two-factor verifications and both passkey authentication paths; `RATE_LIMIT_DEFAULT` (100 per 60s) is where a path starts, not where an unlisted one lands.
- **`customRules` replace a limit, they do not reconcile with it.** Better Auth resolves one in three passes — its built-in special rules, then plugin rules, then `customRules` — and each match overwrites the window and the maximum outright, so an entry here wins whether it is stricter or looser, and `false` removes the limit altogether. Two things follow. Anything starting `/sign-in`, `/sign-up`, `/change-password` or `/change-email` is capped by a built-in rule at **3 per 10 seconds**, so `/sign-in/email`, `/sign-in/social` and `/sign-up/email` are restated in `RATE_LIMIT_RULES` deliberately rather than to cover an uncapped path: 3 per 10s is too tight for a form a household shares an address behind, and `/sign-in/social` is the endpoint behind every OAuth button. Connecting a provider from Settings is a different path, `/link-social`, which no rule matches and which therefore keeps the default. And a path left unlisted keeps whatever the earlier pass gave it instead of falling to the default — the `emailOTP` plugin's 3 per 60s on every path it owns, and the `twoFactor` plugin's 3 per 10s on the `/two-factor/` paths other than the two verifications. The one-time-code limit is left to the plugin because it is already the cap this deployment would choose, not because a rule here could not move it.
- **Those limits are per caller only where the caller can be identified.** Better Auth reads `x-forwarded-for` alone and, with no trusted proxies configured, refuses a header carrying more than one address rather than believing its leftmost hop, which is whatever the client typed. Every request it cannot place is keyed into a single shared bucket per path, so behind a CDN in front of an ingress — or any nginx using `proxy_add_x_forwarded_for` — `/sign-in/email`'s ten attempts a minute become the whole deployment's allowance, and an attacker can spend it deliberately to lock everyone out of signing in. `TRUSTED_PROXIES` (comma-separated addresses or CIDR ranges, passed as `advanced.ipAddress.trustedProxies`) is what makes the chain readable: it is stripped from the right to the first untrusted hop. Trusting a hop is a deployment fact, so it is configuration with no default rather than a guess that would hand every client a spoofable address.
- `auth.accountExists` is capped by a **second, independent limiter**: `packages/api/src/lib/rate-limit.ts` counts it in the same `rate_limit` table under an `account-exists:` key prefix, in one `INSERT … ON CONFLICT DO UPDATE … RETURNING` statement, because a read-then-write lets concurrent callers all pass a stale count. It identifies the caller by asking Better Auth — `getIP(headers, auth.options)` — rather than reading headers itself, so the two limiters cannot disagree about who the caller is, and an unplaceable caller shares one `untrusted` bucket instead of minting a fresh one per request. An earlier version read a wider list of forwarded headers leftmost-first: wider than Better Auth's own `DEFAULT_IP_HEADERS` (`x-forwarded-for` alone), and spoofable, since appending a header bought a new bucket on every call.
- `packages/auth/src/policy.ts` holds every threshold in one place, and holds more of them than when this was written: `session.expiresIn` and `session.freshAge` are `SESSION_EXPIRY_SECONDS` rather than Better Auth's defaults, which is what decision 5's correction cost — a number the active-sessions screen depends on stops being inherited silently. `packages/api`'s `auth.capabilities` procedure publishes the part a screen has to know — `emailDelivery`, `maxPasswordLength`, `minPasswordLength`, `oauth[]`, `otpLength`, `passkey`, `trustedDeviceDays` — so the sign-in screen renders from what the server actually offers instead of from build-time flags, and no field quotes a bound or a code length the server does not enforce. It describes the deployment, never whether a given address has an account; `auth.accountExists` is the one procedure that does, and it is the one that is capped.
- The cookie policy is derived rather than configured, apart from the one declared parent domain — decision 6 records what it decides and what leaving `AUTH_COOKIE_DOMAIN` unset costs a split deployment.
- `BETTER_AUTH_SECRET` is load-bearing for more than sessions: two-factor secrets and backup codes in `two_factor` are encrypted with it, the session-token cookie and the trusted-device cookie are signed with it. Rotating it signs everyone out, ends every trusted device, and leaves existing two-factor enrolments undecryptable — users re-enrol. Registered passkeys survive it, since a stored public key is not a secret.
- Adding a transport is one file in `packages/email/src/providers/`, one `EMAIL_PROVIDER` enum member, and one `switch` arm in the registry. Adding an OpenID Connect provider is configuration only — `packages/auth/src/providers.ts` registers the generic connector under the single id `oidc`, with `requireIdTokenVerification: true`, so a discovery document that supplies no `issuer` and `jwks_uri` fails the server's startup rather than leaving it trusting an unverified `sub`.
