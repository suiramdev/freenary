This page lists the commands an operator runs on a live instance. Each one targets the Docker Compose stack of [Install with Docker Compose](/docs/self-hosting/docker-compose). Run every command from the directory that holds `docker-compose.yml` and the `.env` file next to it, because Compose reads both from the working directory. That directory needs no clone of the repository.

## Routine commands

### Read the service state

```bash
docker compose ps
```

The `STATUS` column shows `healthy` for each of the three long-lived services. A service in `starting` state has not passed its healthcheck yet. A service in `unhealthy` state failed 5 checks in a row. Add `-a` to list the one-shot `migrate` container too, which must show `Exited (0)`.

### Restart one service

```bash
docker compose restart server
```

Replace `server` with `web` or `postgres`. A restart starts the same container again, so the container keeps the environment Compose gave it at creation.

### Apply a new value from `.env`

```bash
docker compose up -d server
```

Compose reads the root `.env` file again, and it recreates each container whose configuration changed. A restart cannot do that. The web app takes a new public API origin the same way, with `docker compose up -d web`, and it needs no new image.

### Read the logs

```bash
docker compose logs -f --tail=100 server
```

Drop the service name to follow all three. Read [Logs](/docs/self-hosting/logs) for the shape of each line and for what the API server does not log.

### Open a database shell

```bash
docker compose exec postgres psql -U postgres -d freenary
```

The role is `postgres` and the database is `freenary`. Both are literal values in `docker-compose.yml`.

### Read the migration state

```bash
docker compose exec -w /app/packages/db server bun x prisma migrate status
```

The command lists the migrations of the image and the ones the database holds. The `migrate` service applies the rest on every `docker compose up`, so a manual `bun x prisma migrate deploy` in the same container is a fallback and not a routine step.

### Pull the published images

```bash
docker compose pull
docker compose up -d
```

`pull` fetches the images that the `FREENARY_VERSION` tag names now. `up -d` then recreates each container that changed, and it runs `migrate` again. Read [Updates](/docs/self-hosting/updates).

### Prune old images

```bash
docker image prune -f
```

Each update leaves the previous image without a tag. This command deletes those, and it keeps every image a container uses.

### Check the disk use of the volume

```bash
docker compose exec postgres du -sh /var/lib/postgresql
docker system df -v
```

The first command measures the database itself. The second lists every Docker volume with its size, and the database volume appears as `freenary_freenary_postgres_data`.

### Stop and start the whole stack

```bash
docker compose down
docker compose up -d
```

<Callout type="error">

Never add `-v` to `docker compose down`. The flag deletes the named volume, and the volume holds the whole database.

</Callout>

## A suggested schedule

Freenary needs no fixed schedule. This one keeps an instance recoverable.

| Task | Command | Suggested frequency |
| --- | --- | --- |
| Back up the database | See [Backup and restore](/docs/self-hosting/backup-and-restore) | Daily |
| Read the service state | `docker compose ps` | Daily |
| Read the logs of the API server | `docker compose logs --tail=100 server` | Weekly |
| Check the disk use of the volume | `docker compose exec postgres du -sh /var/lib/postgresql` | Monthly |
| Update to a newer version | `docker compose pull && docker compose up -d`, see [Updates](/docs/self-hosting/updates) | Monthly |
| Prune old images | `docker image prune -f` | After each update |
| Test a restore into a throwaway database | See [Backup and restore](/docs/self-hosting/backup-and-restore) | Twice a year |
| Rotate `BETTER_AUTH_SECRET` | See [Security](/docs/self-hosting/security) | Only after a leak |

## What Freenary does not do for you

Freenary runs two web processes and nothing else. It has no worker, no scheduler and no cron entry. Four jobs are yours.

| Freenary does not do this | You must do this |
| --- | --- |
| Refresh a bank connection on a schedule. A sync runs only when a user opens the budget page, or presses a sync button. | Tell your users to open the budget page for fresh transactions. |
| Run a scheduled job of any kind. | Put anything periodic in your own scheduler on the host. |
| Rotate any log. | Cap the container output in the Docker daemon, with a `max-size` option. |
| Take a backup. | Add the `pg_dump` command of [Backup and restore](/docs/self-hosting/backup-and-restore) to your own scheduler. |

<Callout type="info">

Three product areas appear in the sidebar of the web app with a **Planned** badge: portfolio, analysis and goals. Freenary does not build them yet, and they need no operator work. The assistant on the Home screen is built, and one decision is yours: the model endpoint. With no endpoint, each reader runs a model in their own browser, which needs nothing from you. Read [Assistant](/docs/self-hosting/assistant).

</Callout>
