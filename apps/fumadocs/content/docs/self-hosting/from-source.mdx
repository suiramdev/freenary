The published images fit a normal install, so a build of your own is one of three cases.

## When an operator needs this

| Case | Why the published image does not fit |
| --- | --- |
| You changed the source | Your patch is in no published tag |
| You run a fork | The merchant data comes from the repository you name at build time |
| Your host cannot pull from GHCR | The build takes the base image `oven/bun:1` instead |

Both published images join `linux/amd64` and `linux/arm64`, so a build for another architecture is not one of the cases.

## Before you build

| You need | Detail |
| --- | --- |
| A checkout of the repository | The build context is the repository root |
| Docker Compose version 2, with BuildKit | The API server build mounts a build secret |
| Outbound network access | The build pulls `oven/bun:1` and it fetches the merchant data |
| The root `.env` file | The same file a published-image install needs |

[Configuration](/docs/self-hosting/configuration) holds every variable of that file. A build reads none of them: the file `.dockerignore` keeps every `.env` file out of the image layers. The configuration arrives at run time.

## Build both images with Compose

A comment at the top of `docker-compose.yml` names the change: replace each `image:` line with a `build:` block. The `migrate` and `server` services share the API server image, so both take the same block.

```yaml
migrate:
  build:
    context: .
    dockerfile: apps/server/Dockerfile
server:
  build:
    context: .
    dockerfile: apps/server/Dockerfile
web:
  build:
    context: .
    dockerfile: apps/web/Dockerfile
```

Then build and start the stack:

```bash
docker compose up -d --build
```

The first build takes several minutes. The API server build downloads or generates the merchant dictionary.

## Build the API server image by hand

A fork needs two values that Compose declares for neither service. Build that one image directly instead:

```bash
export GITHUB_TOKEN=<personal-access-token>
docker build -f apps/server/Dockerfile \
  --build-arg GITHUB_REPOSITORY=my-org/freenary \
  --secret id=GITHUB_TOKEN,env=GITHUB_TOKEN \
  -t freenary-server .
```

| Value | What it does |
| --- | --- |
| `GITHUB_REPOSITORY` | Names the repository the merchant data release comes from. It defaults to `suiramdev/freenary` |
| `GITHUB_TOKEN` | Lifts the GitHub API rate limit of the download. BuildKit mounts it as a secret, so it never enters a layer |

Then write `image: freenary-server` on both the `migrate` and the `server` service.

### The merchant data step

The build step is one download with one fallback.

| Case | What the build does |
| --- | --- |
| The download succeeds | It unpacks the release asset. This is the fast path |
| The download fails | It generates the data from its sources, which takes much longer |
| No outbound access | Neither path completes, and the build fails |

[Categorisation](/docs/contributing/categorisation) covers the dictionary and the classifier weights the step produces.

## What each image holds

| Image | Contents |
| --- | --- |
| API server | The whole build tree from the builder stage, with `node_modules`, the merchant data under `packages/api/data`, and the bundle `dist/index.mjs` |
| Web app | The whole build tree, with the Nitro output `.output/server/index.mjs` |

| Setting | API server | Web app |
| --- | --- | --- |
| Base image | `oven/bun:1` | `oven/bun:1` |
| `NODE_ENV` in the image | `production` | `production` |
| Exposed port | `3000` | `3001` |
| Command | `bun dist/index.mjs` | `bun .output/server/index.mjs` |
| `HEALTHCHECK` instruction | none. Compose declares the check | none. Compose declares the check |
| `USER` instruction | none | none |

The API server image keeps the development dependencies of the build. That is why the `prisma` CLI is available at run time. It is also why the `migrate` service runs from the same image.

## Run the apps with no Docker

This path suits a host that already runs its own PostgreSQL and its own process supervisor. You need Bun `1.3.14` and a PostgreSQL 18 server with a database and a role.

<Steps>

<Step>

### Install the dependencies

```bash
bun install
```

</Step>

<Step>

### Write `apps/server/.env`

The API server process loads a `.env` file from the directory it starts in, and it starts in `apps/server`. The Prisma CLI reads the same file. Compose plays no part here, so that file carries `NODE_ENV` too:

```dotenv
NODE_ENV=production
BETTER_AUTH_SECRET=<auth-secret>
BETTER_AUTH_URL=https://api.example.com
CORS_ORIGIN=https://app.example.com
DATABASE_URL=postgresql://freenary:<database-password>@127.0.0.1:5432/freenary
```

</Step>

<Step>

### Apply the migrations

```bash
cd packages/db && bun x prisma migrate deploy && cd ../..
```

</Step>

<Step>

### Fetch the merchant data and build

```bash
bun run build:data
bun run build
```

</Step>

<Step>

### Start the API server

```bash
cd apps/server && bun run start
```

The port is `PORT`, which defaults to `3000`. Keep `BETTER_AUTH_URL` in step with any change to it.

</Step>

<Step>

### Start the web app in a second shell

```bash
cd apps/web && HOST=0.0.0.0 PORT=3001 PUBLIC_SERVER_URL=https://api.example.com bun .output/server/index.mjs
```

`PUBLIC_SERVER_URL` hands the browser the public API origin at run time. It wins over the value the build inlined.

</Step>

</Steps>

<Callout type="info">

This is not the contributor workflow. A contributor runs the development stack, which watches the files and applies the migrations. Read [The development stack](/docs/contributing/local-stack).

</Callout>
