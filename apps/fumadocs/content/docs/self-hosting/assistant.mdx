Freenary ships with no model. Name an endpoint and a model id, and the API server answers through it: every reader gets that model by default. Name neither, and each reader answers through a model in their own browser. A reader whose browser has WebGPU can pick a browser model on either kind of instance. This page covers the three variables, the endpoints that work, where the variables go in each stack, the rate limit, what each question sends out of the instance, and what the browser model asks of you.

## What the assistant needs

Three optional variables in the validated server schema. None of them has a default.

<TypeTable
  type={{
    AI_BASE_URL: {
      description:
        "The base URL of an OpenAI-compatible chat-completions endpoint, with the version path, for example https://openrouter.ai/api/v1.",
      type: "URL",
      default: "unset",
      required: false,
    },
    AI_API_KEY: {
      description:
        "The key for that endpoint. Optional, because a local runtime needs none.",
      type: "string",
      default: "unset",
      required: false,
    },
    AI_MODEL: {
      description:
        "The model id, exactly as the endpoint names it, for example anthropic/claude-3.5-sonnet or qwen2.5:14b.",
      type: "string",
      default: "unset",
      required: false,
    },
  }}
/>

**`AI_BASE_URL` and `AI_MODEL` together decide whether the assistant answers on the server.** Both must hold a value. With either one empty, the API server reports no server model, and the model list of the reader holds the browser models alone. `AI_API_KEY` never takes part in that test, because a local runtime accepts a call with no key.

Freenary defaults none of the three, and that choice is deliberate. An instance with no endpoint sends no financial data to a third party, and it still answers, because the reader then runs a model in their own browser. Read [the browser model](#the-browser-model).

`AI_BASE_URL` must parse as a URL. A bad value stops the API server at startup, like every other bad value in the [configuration reference](/docs/self-hosting/configuration).

## Point the assistant at an endpoint

A hosted gateway needs all three variables:

```dotenv
AI_BASE_URL=https://openrouter.ai/api/v1
AI_API_KEY=sk-...
AI_MODEL=anthropic/claude-3.5-sonnet
```

A local runtime on the same Docker network needs two:

```dotenv
AI_BASE_URL=http://ollama:11434/v1
AI_MODEL=qwen2.5:14b
```

Freenary calls the endpoint through the `@ai-sdk/openai-compatible` client. It names that client `freenary-assistant`, which identifies the provider inside the API server, in its logs and in its error messages. The name reaches no request: the client sends no extra header and no extra field, so a hosted provider sees a plain chat-completions call.

## Which endpoints work

The assistant accepts any endpoint that speaks the OpenAI chat-completions protocol.

| Kind | Examples | Key |
| --- | --- | --- |
| A gateway in front of many models | OpenRouter, Groq, Together | needed |
| A model vendor | OpenAI | needed |
| A runtime on your own hardware | Ollama, LM Studio, vLLM | usually none |

<Callout type="warn">

**The model must support tool calling.** The assistant reads the money data of a user through read-only lookups, and each lookup is a tool call. A model without tool calling still answers. It answers about the money of the reader, and it reads none of it, so it invents every figure. That result is worse than a refusal, and no error reports it.

Pick a model whose provider documents tool calling. Then ask one question that needs a figure, and check the answer before other people use the instance.

</Callout>

**The model must also follow a small grammar for charts.** An answer whose figures form a series ends with a chart, written in [OpenUI Lang](https://www.openui.com/) and drawn by the web app from five registered components. A model that cannot keep to that grammar still answers in prose; under it the user reads **The chart could not be drawn.** Ask one question that compares several months, and check that a chart appears.

## Where the variables go

The two stacks read the three variables from different places.

| Stack | Where you set them | How they arrive |
| --- | --- | --- |
| Development, `compose.dev.yml` | your own shell, or the root `.env` file | The compose file passes `AI_BASE_URL`, `AI_API_KEY` and `AI_MODEL` through from the host environment, each with an empty default |
| Production, `docker-compose.yml` | `apps/server/.env` | The `server` service loads that file through its optional `env_file` |

`docker-compose.yml` names none of the three in the `environment:` block of the `server` service. So nothing in the compose file wins over your file, and `apps/server/.env` is the one place the three variables belong. Restart the service after a change:

```bash
docker compose up -d server
```

The `server` container must reach a local runtime over the network. Give the runtime a service on the same compose network, then use that service name in `AI_BASE_URL`, as the second example above does. The value `http://localhost:11434/v1` names the container itself, and it reaches nothing.

## The rate limit

One account can ask **30 questions per 5 minutes**. The code fixes that limit, and no variable changes it.

The key is the user id, not the caller address. Every other limit of the instance keys on the address, as [Security](/docs/self-hosting/security#rate-limits) shows. This one is different on purpose. Each question is a paid request at your provider, so the cost follows the account that asks. One busy office behind one address also keeps a full allowance per person.

Over the limit, the screen asks the user to wait, and the chat route answers 429.

The same allowance counts a browser answer. `assistant.saveTurn`, the procedure that stores a turn the browser answered, consumes the same 30 per 5 minutes: the model cost the instance nothing, but each turn still writes two rows. Over the limit the answer still shows on the screen, the turn is not stored, and the screen asks the user to wait.

Each stored question and answer adds database rows, so the database grows with use. Freenary deletes those rows with their user.

## What leaves the instance

A configured endpoint receives financial data. Each question sends all of this to `AI_BASE_URL`:

| What | Detail |
| --- | --- |
| The question | The text the user typed |
| The conversation so far | Every stored question and answer of the active conversation |
| The result of every lookup | Account names, institution names, transaction descriptors, amounts, dates, and category and group slugs |

**Freenary sends no IBAN.** The accounts lookup reports the account id, the account name and the institution name. No lookup takes an IBAN as an input.

A hosted gateway holds everything in the table above, under its own terms. A local runtime keeps all of it on your own hardware, and no money data leaves the host. That choice is the whole difference between the two `AI_BASE_URL` examples above.

Two things never leave the instance for the charts. `@openuidev/lang-core`, the library behind the chart grammar, ships an installation-time telemetry script; Bun runs no lifecycle script of an untrusted package, so it never runs. Its runtime telemetry stays off unless `OPENUI_RUNTIME_TELEMETRY_ENABLED` is set, and Freenary never sets it.

<Callout type="info">

An unset `AI_BASE_URL` sends no financial data anywhere, and the API server makes no outbound call for the assistant at all. One outbound call remains, and the browser of the reader makes it: the download of the browser model from `https://huggingface.co`.

</Callout>

## The browser model

Every reader whose browser has WebGPU can run the assistant on their own device, on a model from [WebLLM](https://github.com/mlc-ai/web-llm). The reader picks that model inside the conversation, the browser downloads it once from the Hugging Face CDN, and the graphics card of the reader runs it. You set no variable for it, and you cannot switch it off. [The assistant](/docs/guides/assistant#choose-a-model) walks the reader through the choice.

An instance with no `AI_BASE_URL` and no `AI_MODEL` therefore still answers questions. Its model list holds the browser models alone, and the reader must pick one before the text box accepts a question.

| Concern | What the browser model means |
| --- | --- |
| Your work | None. You set no variable, and you install no runtime |
| What the reader needs | A browser with WebGPU, and enough graphics memory for the model. Without WebGPU the model list offers no browser model, and it states why |
| Outbound traffic | The one-time model download from `https://huggingface.co` to the browser of the reader. No question and no lookup result leaves the browser |
| Load on the instance | The lookups only. A browser answer makes no model call to the API server, and it does not use `POST /ai/chat` |
| The rate limit | The same 30 stored turns per 5 minutes, as [the rate limit](#the-rate-limit) above states |
| The transcript | The browser stores each finished turn through the `assistant.saveTurn` procedure, in the same two tables a server answer writes. That holds on every instance |
| Answer quality | Lower. A model that fits in a browser is small, so it can pick the wrong lookup, name the wrong period or fail to draw a chart |

`AI_BASE_URL` and `AI_MODEL` do not take the browser model out of the product. With both set, the model list gains one more entry, the id in `AI_MODEL`, and that entry answers by default. A reader can still pick a browser model, and `assistant.saveTurn` then stores the turn. One transcript can therefore hold turns from both. [Procedure reference](/docs/integrations/procedures#assistantsaveturn) holds that procedure.
