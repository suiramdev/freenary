An update is a pull and a restart. The `migrate` service applies each pending migration for you.

## Before you update

<Steps>

<Step>

### Dump the database

A migration can rewrite rows, and a dump is the only way back. Read [Backup and restore](/docs/self-hosting/backup-and-restore).

</Step>

<Step>

### Record the build you run now

```bash
docker compose images server web
```

The command prints the tag and the image ID of each service. Keep both lines. The tags `main` and `dev` move with every push, so the image ID is the exact record.

</Step>

</Steps>

## The tags GHCR holds

The two images are `ghcr.io/suiramdev/freenary-server` and `ghcr.io/suiramdev/freenary-web`. `FREENARY_VERSION` in the root `.env` file names the tag of both.

| Tag | What publishes it |
| --- | --- |
| `main` | A push to the `main` branch. The tag moves with each push |
| `dev` | A push to the `dev` branch. The tag moves with each push |
| `sha-<7 characters>` | The same push. The tag names one commit and never moves |
| `X.Y.Z`, `X.Y`, `X`, `latest` | A `vX.Y.Z` tag, which only the Release workflow creates |
| `X.Y.Z-<pre>` | A `vX.Y.Z-<pre>` tag. It publishes that one tag alone |

Three more facts about the tags:

- A push that touches only `apps/fumadocs/` or a `.md` file publishes no image.
- Each tag joins `linux/amd64` and `linux/arm64` in one manifest.
- The compose default is `latest`, and GHCR holds no such tag until a maintainer cuts a release.

Pin one commit for a production instance:

```dotenv
FREENARY_VERSION=sha-1a2b3c4
```

The package pages of both images list every tag the registry holds. [Release a version](/docs/contributing/releasing) covers the branch model behind them.

## Move the stack to the new tag

<Steps>

<Step>

### Set the tag

Edit `FREENARY_VERSION` in the root `.env` file. An update can add a variable to `.env.example`, so read that file too. [Configuration](/docs/self-hosting/configuration) holds every variable.

</Step>

<Step>

### Pull the images

```bash
docker compose pull
```

</Step>

<Step>

### Recreate the containers

```bash
docker compose up -d
```

Compose recreates each container whose image or configuration changed. The `postgres` container and its volume stay as they are.

</Step>

<Step>

### Check the result

```bash
docker compose ps -a
curl http://localhost:3000/
```

The `migrate` container must show `Exited (0)`. The other three must show `healthy`. The API server must answer `OK`. Then sign in and open one page that lists transactions.

</Step>

</Steps>

The `-a` flag matters. Plain `docker compose ps` lists the running containers alone, and `migrate` has already exited.

## The migration runs on every start

The `migrate` service is one-shot. It runs `bun x prisma migrate deploy` from the server image, in the working directory `/app/packages/db`.

| Order | What happens |
| --- | --- |
| 1 | `migrate` waits until the `postgres` healthcheck passes |
| 2 | `migrate` applies every migration the database does not hold |
| 3 | `server` starts, because it waits for `migrate` to complete successfully |

The step is idempotent. An update with no new migration still exits `0` and changes nothing. Read what it did:

```bash
docker compose logs migrate
```

## Roll back

An update has two halves, and only one of them goes back on its own.

| Half of the update | Goes back |
| --- | --- |
| The two container images | Yes, when you recorded a `sha-` tag or an image ID |
| The database schema and the data | No. The repository ships no reverse migration |

Prisma applies migrations forward only. One shipped migration drops a column, and another remaps every category value. So an older image can meet a schema it does not expect.

<Callout type="warn">

A rollback without a restore leaves the new schema under the old code. Do not skip the restore.

</Callout>

<Steps>

<Step>

### Stop the two apps

```bash
docker compose stop web server
```

</Step>

<Step>

### Restore the dump you took before the update

Read [Backup and restore](/docs/self-hosting/backup-and-restore) for the commands.

</Step>

<Step>

### Name the old tag

Set `FREENARY_VERSION` to the `sha-` tag you recorded.

</Step>

<Step>

### Start the stack again

```bash
docker compose up -d
docker compose ps -a
```

</Step>

</Steps>
