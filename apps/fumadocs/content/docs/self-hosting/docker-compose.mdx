This page installs one Freenary instance from the published images. It covers the two files you need, the root `.env` file, the start command, and the two health checks. Follow the steps in order.

Before you start you need a Linux host with Docker, and the four decisions from [Self-hosting](/docs/self-hosting).

Every command is complete. A value in angle brackets, such as `<database-password>`, is yours to choose. Replace the brackets with it.

## Install

<Steps>

<Step>

### Get the two files

The stack runs published images, so it needs no source code. Two files are enough: `docker-compose.yml` and the template `.env.example`.

```bash
mkdir freenary && cd freenary
curl -O https://raw.githubusercontent.com/suiramdev/freenary/main/docker-compose.yml
curl -O https://raw.githubusercontent.com/suiramdev/freenary/main/.env.example
```

A clone gives you the same two files, plus the source for a [build from source](#build-from-source):

```bash
git clone https://github.com/suiramdev/freenary.git
cd freenary
```

Every command below runs from that directory.

</Step>

<Step>

### Create the environment file

The root `.env` file configures the whole stack. Copy the template:

```bash
cp .env.example .env
```

The template holds development values for the two required variables, and a real instance replaces both. Generate them:

```bash
openssl rand -hex 16   # POSTGRES_PASSWORD
openssl rand -hex 32   # BETTER_AUTH_SECRET, 32 characters or more
```

A file written from scratch works too. These lines are the minimum for a real instance:

```dotenv
POSTGRES_PASSWORD=<database-password>
BETTER_AUTH_SECRET=<auth-secret>
BETTER_AUTH_URL=https://api.example.com
CORS_ORIGIN=https://app.example.com
EMAIL_PROVIDER=smtp
EMAIL_FROM="Freenary <no-reply@example.com>"
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=no-reply@example.com
SMTP_PASSWORD=<smtp-password>
```

`POSTGRES_PASSWORD` and `BETTER_AUTH_SECRET` are required, and neither one has a fallback. Replace `api.example.com` with the public hostname of the API server, and `app.example.com` with the public hostname of the web app. A purely local instance needs neither URL line: `BETTER_AUTH_URL` defaults to `http://localhost:3000`, and `CORS_ORIGIN` defaults to `http://localhost:3001`.

`EMAIL_PROVIDER=resend` needs `RESEND_API_KEY` and `EMAIL_FROM` instead of the five `SMTP_*` lines. Read [Email](/docs/self-hosting/email) for both adapters. Read [Configuration](/docs/self-hosting/configuration) for every other variable.

<Callout type="info">

`.env` is the one environment file of the stack. `apps/server/.env` and `apps/web/.env` play no part in it. Those two files matter only for [Run from source without Docker](#run-from-source-without-docker).

</Callout>

Compose reads the file in two ways:

| How | Which keys | What it sets |
| --- | --- | --- |
| Interpolation into `docker-compose.yml` | `POSTGRES_PASSWORD`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `CORS_ORIGIN`, `FREENARY_VERSION`, `WEB_PORT`, `SERVER_PORT`, `POSTGRES_PORT` | The image tags, the published ports, the database password and the two public URLs |
| `env_file: .env` on the `server` service | Every line of the file | The bank provider, the email provider, the sign-in providers and the assistant reach the API server this way |

The `environment` block of the `server` service overrides the file for five names: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `CORS_ORIGIN` and `NODE_ENV`. Three of the five come from your `.env` file by interpolation, so the value stays yours. The other two are fixed: `DATABASE_URL` always points at the `postgres` service, and `NODE_ENV` is always `production`. A `DATABASE_URL` or a `NODE_ENV` line in `.env` therefore changes nothing in the container.

The `web` service loads no environment file. It takes two values from Compose: `SERVER_URL=http://server:3000`, which its own server calls while it renders a page, and `PUBLIC_SERVER_URL`, the public API origin the browser calls. `PUBLIC_SERVER_URL` follows `BETTER_AUTH_URL`.

</Step>

<Step>

### Start the stack

```bash
docker compose up -d
```

Compose pulls both images, starts PostgreSQL, runs the `migrate` service against it, then starts the API server and the web app. `server` waits until `migrate` exits `0`, so a fresh database holds the whole schema before the first request arrives. `bun run docker:up` runs the same command.

`FREENARY_VERSION` selects the image tag, and it defaults to `latest`, which is the newest release. Pin a version for a production instance:

```dotenv
FREENARY_VERSION=1.2.0
```

The tag `dev` tracks the `dev` branch and holds unreleased code. Read [Updates](/docs/self-hosting/updates).

An empty `POSTGRES_PASSWORD` or `BETTER_AUTH_SECRET` stops the command before any container starts, and Compose names the variable it needs:

```bash
error while interpolating x-database-url: required variable POSTGRES_PASSWORD is missing a value: Set POSTGRES_PASSWORD in .env
```

The `migrate` service makes a separate migration step unnecessary. The manual command still works, and it is still idempotent, for an operator who wants to apply the migrations by hand:

```bash
docker compose exec -w /app/packages/db server bun x prisma migrate deploy
```

</Step>

<Step>

### Check the result

Ask the API server for its health endpoint. It answers with the plain string `OK`:

```bash
curl http://localhost:3000/
```

```http
OK
```

Ask the web app for its root page. It answers `200`:

```bash
curl -o /dev/null -w '%{http_code}\n' http://localhost:3001/
```

```http
200
```

Read the service state with `docker compose ps`. The `migrate` service shows `Exited (0)`, and `postgres`, `server` and `web` must all show `healthy`. If one does not, read [Troubleshooting](/docs/self-hosting/troubleshooting).

</Step>

<Step>

### Create the first account

Open the web app in a browser and sign up with an email address and a password. Freenary has no separate admin account and no owner role: the first account is an ordinary user.

The new user then walks through onboarding. Read [First steps](/docs/guides/first-steps).

</Step>

</Steps>

## Behind a reverse proxy

Put a TLS terminator in front of the two published ports. Send the web app hostname to the web port, `3001` by default, and the API server hostname to the API port, `3000` by default.

Three values must hold the public URLs, not the container ports. All three come from the root `.env` file:

| Variable | Value | Where you set it |
| --- | --- | --- |
| `BETTER_AUTH_URL` | The public URL of the API server | `.env` |
| `CORS_ORIGIN` | The public URL of the web app | `.env` |
| `PUBLIC_SERVER_URL` | The public URL of the API server, for the browser | `.env`, through `BETTER_AUTH_URL`. The `web` service takes that same value |

Use `https://` in all three. The session cookie takes its `Secure` flag from the scheme of `BETTER_AUTH_URL`.

### Two subdomains

A split like `app.example.com` and `api.example.com` needs one more variable. Set `AUTH_COOKIE_DOMAIN` to the shared parent domain:

```dotenv
AUTH_COOKIE_DOMAIN=.example.com
```

With it, the session cookie stays `SameSite=Lax` and carries `Domain=.example.com`. Without it, the cookie drops to `SameSite=None`, and a browser that blocks third-party cookies drops the session. The API server refuses a value that is a single label, ends in a dot, or is not a parent of both hostnames.

### Trusted proxies

Set `TRUSTED_PROXIES` to the addresses or CIDR ranges of every proxy in front of the API server:

```dotenv
TRUSTED_PROXIES=10.0.0.0/24,192.0.2.10
```

The rate limiter keys each counter on the caller address, which it reads from the `x-forwarded-for` header. With the list empty and more than one address in that header, the API server resolves no caller address. In production it then keys every request as `no-trusted-ip` plus the path. One shared bucket per path serves the whole instance, so one visitor can spend the whole sign-in allowance of every user. Read [Security](/docs/self-hosting/security).

## Build from source

The published images fit every deployment, so a build is optional. This path needs the source, so clone the repository first.

A comment at the top of `docker-compose.yml` states the change: replace each `image:` line with the `build:` block of that app. The `migrate` and `server` services share the API server image, so both take the same block:

```yaml
migrate:
  build:
    context: .
    dockerfile: apps/server/Dockerfile
server:
  build:
    context: .
    dockerfile: apps/server/Dockerfile
web:
  build:
    context: .
    dockerfile: apps/web/Dockerfile
```

Then build and start:

```bash
docker compose up -d --build
```

The first build takes several minutes, because the API server build downloads or builds the merchant dictionary.

A fork needs two more values for that step. The build argument `GITHUB_REPOSITORY` names the repository the dictionary comes from, and it defaults to `suiramdev/freenary`. The build secret `GITHUB_TOKEN` lifts the GitHub API rate limit, and it never reaches the image. Compose declares neither, and a build secret also needs a top-level `secrets:` entry, so a manual build of the API server image is simpler. Export a token first, then:

```bash
export GITHUB_TOKEN=<personal-access-token>
docker build -f apps/server/Dockerfile \
  --build-arg GITHUB_REPOSITORY=my-org/freenary \
  --secret id=GITHUB_TOKEN,env=GITHUB_TOKEN \
  -t freenary-server .
```

Name that image in `docker-compose.yml` with `image: freenary-server` on both `migrate` and `server`. Read [Updates](/docs/self-hosting/updates#when-the-image-build-cannot-reach-the-release) for what the build does when the download fails.

## Run from source without Docker

This path suits a host that already runs its own PostgreSQL and its own process supervisor. You need Bun `1.3.14` and a PostgreSQL 18 server with a database and a role.

Install the dependencies:

```bash
bun install
```

In this path the API server process reads its variables from `apps/server/.env`. It loads a `.env` file from its working directory, and it starts in `apps/server`. Compose plays no part here, so that file must also carry `NODE_ENV` and the URL of your own database:

```dotenv
NODE_ENV=production
BETTER_AUTH_SECRET=<auth-secret>
BETTER_AUTH_URL=https://api.example.com
CORS_ORIGIN=https://app.example.com
DATABASE_URL=postgresql://freenary:<database-password>@127.0.0.1:5432/freenary
```

Apply the migrations. The Prisma CLI reads `apps/server/.env` for `DATABASE_URL`:

```bash
cd packages/db && bun x prisma migrate deploy && cd ../..
```

Fetch the merchant data, then build all three apps:

```bash
cd packages/api && bun run build:data && cd ../..
bun run build
```

Start the API server on port 3000:

```bash
cd apps/server && bun run start
```

Start the web app on port 3001, in a second shell. `PUBLIC_SERVER_URL` gives the browser the public API origin at run time:

```bash
cd apps/web && HOST=0.0.0.0 PORT=3001 PUBLIC_SERVER_URL=https://api.example.com bun .output/server/index.mjs
```

A build-time value also works, for a host that prefers no runtime variable. Vite inlines `VITE_SERVER_URL` into the browser bundle, so build the web app with it in the environment:

```bash
cd apps/web && VITE_SERVER_URL=https://api.example.com bun run build
```

Set it in that directory, not on the root `bun run build`: the root script runs Turborepo in its strict environment mode, which passes no undeclared variable to the task. The inlined value is the fallback in either case, because `PUBLIC_SERVER_URL` wins over it at run time.

`PORT` sets the API server port too. Change it in `apps/server/.env`, and keep `BETTER_AUTH_URL` in step with it.
