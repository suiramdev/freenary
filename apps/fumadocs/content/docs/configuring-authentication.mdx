description: Email delivery, OAuth and OpenID Connect providers, passkeys, password policy, cookies and rate limits for a self-hosted instance.

Every sign-in method except two is configuration, and every one of those is off until you set it. A fresh instance with none of the variables below still runs, and still signs people in: email and password always works, and so do passkeys, which need no configuration at all. What it cannot do is send an email — so there is no address confirmation and no password reset until you connect a provider. This page covers what to set and what each setting costs you.

The reader-facing description of the flows themselves is [Signing in](/docs/signing-in).

## Email delivery comes first

Email carries exactly two flows: **confirming an address** after sign-up, and **resetting a forgotten password**. Nobody signs in with an emailed code — every account authenticates with a password — so a missing provider does not close the door, it removes the two flows that need a mailbox.

With no `EMAIL_PROVIDER` set, three things follow, and the third is the one to decide deliberately:

- The one-time-code plugin is not registered, so there is **no password reset** anywhere in the product. A user who forgets their password needs an operator with database access.
- `requireEmailVerification` follows the provider, so it is off: sign-up returns a session straight away and no address is ever confirmed.
- With it off, **sign-up reveals whether an address is registered**. Confirmation is what makes sign-up answer identically for a taken address and a free one — both say a code is waiting, neither returns a session. Without it, a taken address fails and a free one signs in.

**Configure an email provider before exposing an instance to the internet.**

`EMAIL_PROVIDER` picks one of three adapters, and `EMAIL_FROM` is the envelope sender for every message Freenary sends:

```dotenv
EMAIL_PROVIDER=smtp
EMAIL_FROM="Freenary <no-reply@example.com>"
```

| Variable | Default | Notes |
| --- | --- | --- |
| `EMAIL_PROVIDER` | unset | `log`, `resend` or `smtp`. Unset means no provider is connected. |
| `EMAIL_FROM` | unset | Required by `resend` and `smtp`. |

A provider that is named but incompletely configured **throws at startup**, naming the variable it wants, rather than accepting a sign-up and swallowing the code. The startup failure is the design: the alternative is an operator watching a healthy process while users stare at a screen that says a code is on its way.

### `resend`

One variable, and the message goes over Resend's REST API.

| Variable         | Default | Notes     |
| ---------------- | ------- | --------- |
| `RESEND_API_KEY` | unset   | Required. |

### `smtp`

Any relay, including one that authenticates by network position rather than credentials — leave `SMTP_USER` unset and no authentication is attempted.

| Variable | Default | Notes |
| --- | --- | --- |
| `SMTP_HOST` | unset | Required. |
| `SMTP_PORT` | `465` when `SMTP_SECURE` is on, otherwise `587` |  |
| `SMTP_SECURE` | `false` | Implicit TLS. Leave off for STARTTLS on 587. |
| `SMTP_USER` | unset | Omit to skip authentication entirely. |
| `SMTP_PASSWORD` | unset | Only read when `SMTP_USER` is set. |

### `log`

Prints each message, one-time code included, to the server log and delivers nothing. It is how the development stack works with no mail account: `compose.dev.yml` defaults `EMAIL_PROVIDER` to `log`, so confirmation and password reset are exercisable out of the box.

It is **refused when `NODE_ENV=production`** — the process fails to start. A development adapter that writes credentials to a log file is indistinguishable from a working transport until someone reads the log, and startup is the last cheap moment to catch that.

## Sign-in providers

Each provider is inert while its variables are unset, and the sign-in screen renders from what the server reports rather than from build-time flags — so an unconfigured provider shows no button rather than a button that fails on click.

Every provider needs one redirect URI registered on its side, and the shape is always the same: `$BETTER_AUTH_URL/api/auth/callback/<id>`, where `<id>` is `google`, `apple` or `oidc`.

`BETTER_AUTH_URL` is the API's public origin. It defaults to `http://localhost:$PORT` (and `PORT` defaults to `3000`), which is fine for development and wrong for anything you register with a provider.

### Google

| Variable | Default | Notes |
| --- | --- | --- |
| `GOOGLE_CLIENT_ID` | unset | Both are required; either one alone leaves Google off. |
| `GOOGLE_CLIENT_SECRET` | unset |  |

Credentials come from the Google Cloud console; register `$BETTER_AUTH_URL/api/auth/callback/google` as the authorized redirect URI.

### Apple

| Variable | Default | Notes |
| --- | --- | --- |
| `APPLE_CLIENT_ID` | unset | The Services ID. Required with the secret. |
| `APPLE_CLIENT_SECRET` | unset | The signed client-secret JWT Apple expects. |
| `APPLE_APP_BUNDLE_IDENTIFIER` | unset | Overrides the audience expected in Apple's ID token, which otherwise is the Services ID. Set it when a native app signs in against this instance. |

Register `$BETTER_AUTH_URL/api/auth/callback/apple`. Apple posts its callback from `https://appleid.apple.com`, so Freenary adds that origin to the trusted list automatically when Apple is configured — you do not add it yourself.

### Any OpenID Connect provider

This is the option that matters most for self-hosting: it covers **Authentik, Keycloak, Zitadel, Entra** and anything else that speaks OpenID Connect discovery, without Freenary shipping a connector per vendor. It registers under the single provider id `oidc`, so the redirect URI is `$BETTER_AUTH_URL/api/auth/callback/oidc`.

| Variable | Default | Notes |
| --- | --- | --- |
| `OIDC_DISCOVERY_URL` | unset | The discovery document, e.g. `https://idp.example.com/.well-known/openid-configuration`. Required. |
| `OIDC_CLIENT_ID` | unset | Required. |
| `OIDC_CLIENT_SECRET` | unset | Omit for a public client. |
| `OIDC_PROVIDER_NAME` | unset | The label users see, e.g. `Acme SSO`. Unset shows a translated "single sign-on" instead — the provider id `oidc` is never rendered. |
| `OIDC_SCOPES` | unset | Comma-separated extras. `openid`, `email` and `profile` are always requested. |

The provider is registered only when **both** `OIDC_DISCOVERY_URL` and `OIDC_CLIENT_ID` are set.

<Callout type="warn">
  ID-token verification is required, so the discovery document must serve an
  `issuer` and a usable `jwks_uri`. The account's identity is the verified `sub`
  claim, and rather than trust an unverified token **authentication fails to
  initialize** — the error names the provider and says discovery did not supply
  them. The document is fetched on **every** start, not cached between them, so
  the same failure comes from a provider that is merely unreachable at that
  moment: with OIDC configured, an identity provider that is down or not yet
  resolvable takes the API process with it, and a restart policy turns that into
  a loop. Keep the discovery URL reachable from the server, or leave
  `OIDC_DISCOVERY_URL` unset until it is.
</Callout>

## Passkeys

Passkeys have **no variables**. The plugin is always registered, credentials live in the `passkey` table, and the sign-in screen offers the button on every deployment; whether a given reader can use it is decided by their browser, not by you.

The relying party — the identity a credential is bound to — is derived, not configured: it is the **hostname of `CORS_ORIGIN`**, the web app's own origin. WebAuthn binds a credential to the origin that created it, and the ceremony runs in the browser on the web app rather than on the API, so `BETTER_AUTH_URL`'s hostname would be the wrong answer in any split deployment. A settable relying-party id would only add a way to break sign-in.

Two consequences follow:

- **Changing `CORS_ORIGIN` invalidates every registered passkey — the port counts.** The relying-party id is the hostname, but verification also compares the **whole origin**: `CORS_ORIGIN` is passed to the plugin as `origin` and reaches SimpleWebAuthn as `expectedOrigin`, which is compared to the origin the browser put in the signed response by exact string. So `https://app.example.com` and `https://app.example.com:8443` are different relying-party origins, and moving between them makes the browser offer a credential the server then refuses. The rows stay in the `passkey` table; users register again on the new origin.
- **WebAuthn requires a secure context.** Browsers treat `https` origins — and `localhost` — as secure, and nothing else: an instance served to real users over plain `http` cannot offer passkeys at all. The Passkeys section detects that and explains it instead of showing a button whose only outcome is an error.

## Password policy

| Variable | Default | Notes |
| --- | --- | --- |
| `AUTH_PASSWORD_BREACH_CHECK` | `true` | Checks new passwords against Have I Been Pwned. |

Email and password is **not switchable**. Every account signs in with a password, and there is no variable that turns that off, so a deployment cannot end up with no way in.

The minimum password length is **twelve characters** and is not configurable. There is no character-class requirement: length is the only rule that reliably raises guessing cost.

`AUTH_PASSWORD_BREACH_CHECK` sends a SHA-1 prefix — never the password, never the full hash — to Have I Been Pwned's range API and refuses a password found there. An **air-gapped deployment has no route to that API at all**, so turn it off there; every other deployment should leave it on.

## Sign-in by an emailed code is refused

A one-time code can confirm an address or reset a password. It can never open an account, and that takes three refusals rather than one:

- **`/sign-in/email-otp` answers `404`** on every deployment. The one-time-code plugin is registered for address confirmation and password reset only, and registering it also exposes that passwordless sign-in route, so the route is refused at the router rather than left reachable.
- **Asking for a sign-in code answers `400` / `INVALID_OTP_TYPE`.** Refusing only the route above would leave `/email-otp/send-verification-otp` mailing "your Freenary sign-in code" to any address named, for a code nothing would accept — an unauthenticated mailer and a ready-made phishing lure. The code purpose is refused, and no such message exists in the copy either.
- **Confirming an already-confirmed address answers `400` / `INVALID_OTP`.** Confirmation signs the user in, which is what makes sign-up work in one step; but the route neither checks nor changes anything for an address that is already confirmed, so without that refusal an emailed code would be a way past both the password and the second factor.

A mailbox is not allowed to be the whole of an account's security. The reasoning, and the account-existence cost that comes with the progressive sign-in form, is [ADR-005](https://github.com/suiramdev/freenary/blob/main/docs/adr/005-sign-in-methods-and-account-linking.md).

## Cookies

| Variable | Default | Notes |
| --- | --- | --- |
| `AUTH_COOKIE_DOMAIN` | unset | The parent domain the API and the web app share, e.g. `.example.com`. Set it when they sit on different subdomains. Three shapes **refuse to start**, because a browser discards a cookie whose `Domain` it cannot match and sign-in would answer 200 with nobody signed in: one that is not a parent of both hostnames, a single label such as `.com` or `.local`, and one ending in a dot. A multi-label public suffix such as `.co.uk` is deliberately **not** detected — telling it from a real domain needs a public-suffix list this project does not ship. |

Everything else about the session cookie is derived at startup from `BETTER_AUTH_URL` (the API) and `CORS_ORIGIN` (the web app):

| API vs web app | `AUTH_COOKIE_DOMAIN` | Session cookie |
| --- | --- | --- |
| Identical hostnames — one origin behind a proxy, or `localhost` on two ports | either | `SameSite=Lax` |
| Different hostnames | set | `SameSite=Lax`, and the cookie carries `Domain=` that value so both origins send it |
| Different hostnames | unset | `SameSite=None`, which browsers honour **only over HTTPS** |

**Set it for a split-subdomain deployment.** Browsers judge same-site by registrable domain, and a registrable domain cannot be derived from a hostname: `api.example.com` and `app.example.com` are same-site, `api.example.co.uk` and `app.example.co.uk` are too, and telling those apart from a pair that merely shares a suffix needs a public-suffix list the server does not carry. So the declared parent domain is the evidence, not a guess — the two cases the server can prove are identical hostnames and an operator naming the domain. Without it a split deployment falls back to `SameSite=None`, which attaches the session, trusted-device and two-factor cookies to cross-site requests — a third-party page's `fetch`, form post or subresource — that `Lax` would leave unauthenticated.

The cookie is always `HttpOnly`, and `Secure` follows whether `BETTER_AUTH_URL` is `https`. Split hostnames, no cookie domain and plain HTTP is the one combination that cannot work: browsers drop a `SameSite=None` cookie without `Secure`, so the server **refuses to start** in production and warns in development. Set `AUTH_COOKIE_DOMAIN`, serve `BETTER_AUTH_URL` over HTTPS, or put the API and the web app behind one hostname.

**The shared cookie is also what lets the web app decide a page on the server.** On every page load the web app's own server forwards the request's cookie to the API and finds out who is asking, so a signed-in visitor gets their home page in the first response and a signed-out one gets the sign-in form — never one and then the other. That only works when the browser sends the session cookie to the web app's origin, which is the first two rows of the table above. In the third — split hostnames, no `AUTH_COOKIE_DOMAIN` — the web app's server never sees a session, treats every page load as undecided, and leaves it to the browser to redirect once it has checked; the app still works, with the bounce that implies. The API reports which case it is in as `sessionCookieShared` in its public `auth.capabilities` answer.

The web app's server reaches the API through `SERVER_URL`, an origin the server can connect to directly — a container name, a private address — that need not be the public `VITE_SERVER_URL` the browser uses. Left unset, it falls back to that public one.

The development stack is itself a split-hostname deployment, over HTTPS: `compose.dev.yml` serves the API at `server.<worktree>.freenary.orb.local` and the web app at `web.<worktree>.freenary.orb.local`. `bun run dev:up` therefore sets `AUTH_COOKIE_DOMAIN` to `.<worktree>.freenary.orb.local` for you, and `SERVER_URL` to the API's container address; a value of your own in the shell or in `.env` wins.

## Rate limits and lockouts

Limits are enforced on every deployment except `NODE_ENV=test` — including development, so you can see them work. Whether they cap the caller or the whole instance depends on one variable.

| Variable | Default | Notes |
| --- | --- | --- |
| `TRUSTED_PROXIES` | unset | The reverse proxies in front of this server, as addresses or CIDR ranges, comma-separated, e.g. `10.0.0.0/24,192.0.2.10`. Every entry is validated at startup and anything that is not an address or a CIDR range **refuses to start**: Better Auth would otherwise drop it and fall back to the shared bucket this variable exists to prevent, so a typo would undo it in silence. An IPv4-mapped IPv6 entry such as `::ffff:10.0.0.0/24` is refused too, even though Better Auth would accept some of them — write the plain IPv4 form, which is what it compares against anyway and is never dropped. |

<Callout type="warn">
  **Set `TRUSTED_PROXIES` if anything sits in front of the server.** The caller
  is read from `x-forwarded-for` alone, and with no trusted proxies a header
  carrying more than one address is refused rather than believed — the leftmost
  hop is whatever the client typed. A CDN in front of an ingress, or any nginx
  using `proxy_add_x_forwarded_for`, produces exactly that chain. When the
  address cannot be resolved, every caller is counted into **one shared bucket
  per path**: `/sign-in/email`'s 10 per 60s becomes the whole deployment's
  allowance, and anyone can spend it on purpose and lock everybody out of
  signing in.
</Callout>

With the list set, the chain is stripped from the right to the first hop that is not a trusted proxy — that is the caller — and an IPv6 address is collapsed to its /64 so a client cannot walk its own prefix for a fresh bucket. In development and test an unresolvable address falls back to `127.0.0.1`, which is also one shared bucket; that is why a local stack behaves as if every browser were the same caller.

| Endpoint | Limit | Set by |
| --- | --- | --- |
| `/sign-in/email` | 10 per 60s | `RATE_LIMIT_RULES` |
| `/sign-in/social` | 10 per 60s | `RATE_LIMIT_RULES` |
| `/sign-up/email` | 5 per 300s | `RATE_LIMIT_RULES` |
| `/two-factor/verify-totp` | 10 per 300s | `RATE_LIMIT_RULES` |
| `/two-factor/verify-backup-code` | 5 per 300s | `RATE_LIMIT_RULES` |
| `/passkey/generate-authenticate-options` | 20 per 60s | `RATE_LIMIT_RULES` |
| `/passkey/verify-authentication` | 20 per 60s | `RATE_LIMIT_RULES` |
| every other `/two-factor/` path — enrolling, disabling, regenerating recovery codes | 3 per 10s | `twoFactor` plugin |
| every one-time-code path — `/email-otp/*`, `/forget-password/email-otp` | 3 per 60s | `emailOTP` plugin |
| any other path starting `/sign-in`, `/sign-up`, `/change-password` or `/change-email` | 3 per 10s | Better Auth built-in |
| `/request-password-reset`, `/send-verification-email`, `/forget-password*` | 3 per 60s | Better Auth built-in |
| everything else under the auth handler | 100 per 60s | `RATE_LIMIT_DEFAULT` |

**The last row is narrower than it looks, and the third column is how to read the table.** Better Auth resolves a limit in three passes — its own built-in rules, then plugin rules, then Freenary's `RATE_LIMIT_RULES` — and every pass that matches overwrites the previous one outright, whether it is looser or stricter. `RATE_LIMIT_DEFAULT` is the starting value, so it survives only on a path that no built-in and no plugin rule matched: an unlisted path under one of those four prefixes is capped at **3**, not 100.

That is why both `/sign-in` rows are restated deliberately. The built-in 3 per 10 seconds is too tight for a form a household shares an address behind, and `/sign-in/social` is the endpoint behind every OAuth button, where a handful of people starting a sign-in at once would otherwise exhaust it. **Connect** in Connected accounts is a different endpoint, `/link-social`, which no built-in, plugin or custom rule matches and which therefore sits on the 100 per 60 seconds default. The one-time-code rows are left to the plugin because 3 per 60 seconds is already the cap we would choose, not because a rule here could not change them: an entry for one of those paths would replace the plugin's, in either direction, and `false` would remove the limit altogether.

Counters live in the database, in the `rate_limit` table, not in process memory: **restarting the server does not clear a lockout**, and a multi-process deployment shares one counter rather than one per worker.

One-time codes are stored hashed, so a database dump carries no code that still opens an account. They are six digits, expire after ten minutes, and are burned after three wrong attempts. None of the three is configurable, and the length is published to the interface as `otpLength` so the code field cannot ask for a number of digits the server does not issue.

### The account-existence limit

One API procedure has its own limit, outside the auth handler: `auth.accountExists` allows **20 calls per 60 seconds** per caller. It exists because the progressive sign-in form asks whether an address has an account before it can decide whether to show a password field or a full sign-up, which makes that answer readable to anyone who can call the procedure.

It is counted in the same `rate_limit` table, under keys prefixed `account-exists:`, and it identifies the caller by asking Better Auth rather than reading headers itself — so the two limiters agree about who the caller is by construction, `TRUSTED_PROXIES` included. A caller the server cannot place shares one `untrusted` bucket instead of getting a fresh one per request. **The cap is a mitigation, not a fix**: it makes enumerating a list of addresses expensive, and does not make a single lookup private.

## The re-authentication window

Changing which credentials open an account needs a session created in the last **fifteen minutes**. Outside it, `/link-social`, `/unlink-account`, `/passkey/delete-passkey` and both halves of passkey registration — `/passkey/generate-register-options` and `/passkey/verify-registration` — answer `403` with `SESSION_NOT_FRESH`, and the interface asks the user to sign in again. Renaming a passkey is not in the list, because it changes nothing about how the account opens.

`/list-sessions` is deliberately outside that window — the screen someone opens _because_ they suspect a problem has to keep working — and that takes one setting as well as the hook. Better Auth gates `/list-sessions` on `session.freshAge`, so Freenary sets `freshAge` to the **seven-day** session lifetime, the same value as `session.expiresIn`: a session's `createdAt` never moves, so anything shorter would make Active sessions fail for the rest of the session's life. The fifteen-minute window comes from the policy hook instead, which is what keeps it off `/list-sessions`.

Neither the window nor the endpoint list is configurable; see [ADR-005](https://github.com/suiramdev/freenary/blob/main/docs/adr/005-sign-in-methods-and-account-linking.md) for why it is a hook rather than a lowered session freshness setting.

## Secrets

`BETTER_AUTH_SECRET` must be at least 32 characters. Its development default (`dev_secret_change_me_at_least_32chars`) is exactly what its name says — replace it before anything reachable.

<Callout type="warn">
  Rotating `BETTER_AUTH_SECRET` is not a quiet operation. Session cookies and
  trusted-device cookies are signed with it, so **everyone is signed out** and
  every "remember this device for 30 days" ends; two-factor secrets and recovery
  codes in the `two_factor` table are encrypted with it, so existing enrolments
  stop working and users must re-enrol. Registered passkeys survive — a stored
  public key is not a secret.
</Callout>
