Three moves take you from a clone to a merged change. Set up the repository, run the stack, then run the same checks CI runs.

## What you need

| Tool | Version | Why you need it |
| --- | --- | --- |
| Bun | `1.3.14` | The runtime, the package manager and the test runner. `packageManager` in the root `package.json` pins it. |
| Docker | Any current release | Both stack paths run PostgreSQL in a container. |
| OrbStack | Any current release | The containerised path only. No development service publishes a host port. |
| PostgreSQL | `18` | The image `bun run db:start` starts for you. You install nothing by hand. |

The repository holds a `.nvmrc` file with the content `v25.6.1`. No script and no workflow reads it. Bun runs everything here.

## Set up

<Steps>

<Step>

### Clone and install

```bash
git clone https://github.com/suiramdev/freenary.git
cd freenary
bun install
```

`bun install` also runs the `postinstall` script of `@freenary/db`, which runs `prisma generate`. The client lands in `packages/db/prisma/generated`. It needs the schema files, not a live database.

</Step>

<Step>

### Build the merchant data once

```bash
bun run build:data
```

The categorisation pipeline reads `packages/api/data/merchants.jsonl.gz`. The development image `.docker/dockerfile.dev` does not build that artifact, and only the production server image does. Run the command on your host before you start the stack. [Transaction categorisation](/docs/contributing/categorisation) covers the artifact.

</Step>

<Step>

### Start the stack

Pick one of the two paths below. Then create your account in the browser.

</Step>

</Steps>

## The two ways to run the stack

One line separates them. The containerised path runs every part in Docker, behind OrbStack hostnames. The local path runs the three applications on your host.

| Path | Command | What you get |
| --- | --- | --- |
| Containerised | `bun run dev:up` | Five services, one HTTPS hostname per application and per worktree, no host port |
| Local | `bun run db:start`, then `bun run dev` | Three host processes on ports `3000`, `3001` and `4000`, with PostgreSQL on `127.0.0.1:5432` |

[Local development stack](/docs/contributing/local-stack) holds the services, the hostnames, the database commands and the first account.

## The checks before a pull request

`.github/workflows/ci.yml` declares two jobs, `ci` and `compose`. GitHub starts both on every pull request, and on every push to `dev` and `main`. The `ci` timeout is 10 minutes and the `compose` timeout is 5 minutes.

The `ci` job runs five commands. Run the same five before you open a pull request:

```bash
bun install --frozen-lockfile
bun run check
bun run check-types
bun run docs:check
bun run build
```

| Order | CI step name | Command | What it covers |
| --- | --- | --- | --- |
| 1 | _(unnamed)_ | `bun install --frozen-lockfile` | The lockfile matches the manifests |
| 2 | Lint & format | `bun run check` | `ultracite check` over the whole repository |
| 3 | Type check | `bun run check-types` | `turbo run check-types` |
| 4 | Documentation | `bun run docs:check` | `turbo run docs:check`, which reaches `apps/fumadocs` |
| 5 | Build | `bun run build` | `turbo run build`, which builds the three applications |

The `compose` job needs no Bun and no install. It checks three things:

- `docker compose -f docker-compose.dev.yml config --quiet` parses the development stack.
- The same command against `docker-compose.yml` parses the production stack, with a temporary `.env` that sets `POSTGRES_PASSWORD` and `BETTER_AUTH_SECRET`.
- The same command with an empty `.env` must fail. A pass means the production file accepted two empty secrets, so the job fails.

That job is the one CI check no root script covers. Reproduce it by hand before you change either compose file.

<Callout type="warn">

`bun run check-types` reaches two workspaces only. `apps/server` and `@freenary/ui` declare the script. `apps/web` declares none. `apps/fumadocs` names its own script `types:check`, so `turbo run check-types` skips it. Type-check those two workspaces by hand before you push.

</Callout>

### Tests run by hand, one file at a time

CI runs no tests. The root `package.json` and all ten workspace manifests declare no `test` script, and `turbo.json` declares no `test` task. Run the files your change touches:

```bash
bun test scripts/dev-identity.test.ts
bun test packages/api/src
```

The repository holds 48 test files outside `node_modules`, each named `*.test.ts` or `*.test.tsx`:

| Location         | Test files |
| ---------------- | ---------- |
| `packages/api`   | 28         |
| `apps/web/src`   | 15         |
| `packages/ui`    | 2          |
| `packages/auth`  | 1          |
| `packages/email` | 1          |
| `scripts`        | 1          |

Assertions sit inside `it()` or `test()`. Suites stay flat, no test uses a done callback, and no `.only` or `.skip` reaches a commit.

## Format and lint

```bash
bun run fix     # ultracite fix, writes the fixes
bun run check   # ultracite check, reports only
```

Both skip Turborepo and cover the whole repository. Ultracite wraps two tools: Oxlint for the rules and Oxfmt for the format.

| File | What it sets |
| --- | --- |
| `oxlint.config.ts` | Extends the Ultracite `core`, `react` and `tanstack` presets. Registers the local `anti-slop` plugin with 15 rules at `error`. Ignores `packages/ui/**`, `apps/web/src/components/ai-elements/**` and `apps/web/src/paraglide/**`. |
| `oxfmt.config.ts` | Spreads the Ultracite format config. It does not ignore `packages/ui/**`, so Oxfmt formats that package and Oxlint does not lint it. |

`lefthook.yml` declares one hook. On `pre-commit` it runs two jobs in parallel:

| Job      | Command                            |
| -------- | ---------------------------------- |
| `oxlint` | `bun oxlint --fix {staged_files}`  |
| `oxfmt`  | `bun oxfmt --write {staged_files}` |

Both set `stage_fixed: true`, so each job re-stages the files it changed. The repository declares no `pre-push` hook and no `commit-msg` hook.

## Branches, commits and pull requests

Two branches live for ever. Every pull request targets `dev`, and `main` holds released code. [Release a version](/docs/contributing/releasing) covers how a version becomes a tag.

Branch names describe the change. `.github/CONTRIBUTING.md` names three good examples and three to avoid:

| Good                             | Avoid     |
| -------------------------------- | --------- |
| `fix/login-redirect-loop`        | `test`    |
| `feat/portfolio-holdings-view`   | `misc`    |
| `chore/update-contributor-guide` | `changes` |

The repository documents no commit-message convention. It holds no commitlint config and no `commit-msg` hook. Write a subject line that names what changed.

### The pull request body

`.github/pull_request_template.md` declares five headings. Fill each one, and keep each one short. The whole body stays near 400 words. The summary stays near four sentences, and the middle three sections near four bullets each.

| Section | What it carries |
| --- | --- |
| Summary | What changed, and what a reviewer reads first. |
| Motivation | Why the change is worth it. |
| Drawbacks | The honest costs. |
| Prior art | The alternatives you rejected. |
| Notes | One line per fact: linked issue, visual change, tests, documentation pages, migration, breaking change. |

Never restate the issue in the body, and never paste command output into it.

### What a reviewer expects

- The pull request opens against `dev`.
- It explains the user-visible change.
- It stays on a single topic.
- It carries screenshots or a screen capture for new interface work. With no visual change, it says so.
- It names the `apps/fumadocs` pages it updated, or states that none needed a change.

A change to documented behaviour owes a documentation update in the same pull request. A screen, an API route, an environment variable, a `packages/db` enum, a script and a bank provider all count. [Writing documentation](/docs/contributing/writing-docs) holds the rules for that update.

Check an interface change in the browser, in light mode and in dark mode. A tag and a version bump are maintainer work, so leave both out.

### Issues

`.github/ISSUE_TEMPLATE/config.yml` sets `blank_issues_enabled: false`, so every issue starts from one of three forms.

| Form            | Title prefix  |
| --------------- | ------------- |
| Bug report      | `[Bug]: `     |
| Feature request | `[Feature]: ` |
| Other           | `[Other]: `   |
