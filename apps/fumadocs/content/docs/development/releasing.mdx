Freenary ships as two container images. This page covers the branch model, the workflow that builds the images, the workflow a maintainer runs to cut a version, and the tags each one produces.

Releases are maintainer work. A contributor opens a pull request against `dev` and stops there.

## The two branches

| Branch | Role                   | What lands on it                   |
| ------ | ---------------------- | ---------------------------------- |
| `dev`  | The integration branch | Every pull request.                |
| `main` | The release branch     | `dev`, at the moment of a release. |

A normal release has two steps. First merge `dev` into `main`. Then run the `Release` workflow from `main`.

A hotfix goes the other way round. Open the pull request against `main`, so the fix does not carry the unreleased work on `dev`. Release from `main` as usual. Then merge `main` back into `dev`, or the fix disappears at the next release.

The root `package.json` carries no `version` field. The git tag is the version, and nothing in the repository repeats it.

## The `Images` workflow

`.github/workflows/images.yml`, named **Images**, publishes both images to the GitHub Container Registry.

| Image                               | Built for                       |
| ----------------------------------- | ------------------------------- |
| `ghcr.io/suiramdev/freenary-server` | `linux/amd64` and `linux/arm64` |
| `ghcr.io/suiramdev/freenary-web`    | `linux/amd64` and `linux/arm64` |

The image name comes from the repository slug in lower case, so a fork publishes under its own owner.

### When it runs

- A push to `dev` or `main`. Two path filters skip the run: `apps/fumadocs/**` and `**/*.md`. A documentation-only push therefore builds nothing.
- A `workflow_call` from the `Release` workflow, with the input `ref`. That input is the git ref to build, such as `refs/tags/v1.2.0`.

Runs of the same ref queue behind each other. The concurrency group never cancels a run in progress.

### The three jobs

| Job | Runner | What it does |
| --- | --- | --- |
| `tags` | `ubuntu-latest` | Reads the ref and derives the version and the tag list. |
| `build` | Per platform, see below | Builds one image for one platform and pushes it by digest. |
| `merge` | `ubuntu-latest` | Joins the digests of one image into one multi-platform manifest, then inspects it. |

`build` is a matrix over the two applications and the two platforms, and each platform builds on its own native runner: `ubuntu-latest` for `linux/amd64`, and `ubuntu-24.04-arm` for `linux/arm64`. The reason is the server build, which runs Bun: Bun under QEMU emulation is slow and unreliable. The matrix sets `fail-fast: false`, so one broken platform still reports the other three results.

Each `build` job pushes with `push-by-digest=true` and attaches no tag. The tags land in `merge`, on the manifest that carries both platforms. `merge` runs `docker buildx imagetools create` with one `-t` per tag and one reference per digest, then `docker buildx imagetools inspect` on the version tag.

The build passes the build argument `GITHUB_REPOSITORY` and the secret `GITHUB_TOKEN`, which `apps/server/Dockerfile` needs for the merchant data. [Architecture](/docs/development/monorepo#build-and-cache) covers that step.

### The tags

| Ref                | Tags on both images                              |
| ------------------ | ------------------------------------------------ |
| Push to `dev`      | `dev`, `sha-<first 7 characters of the commit>`  |
| Push to `main`     | `main`, `sha-<first 7 characters of the commit>` |
| Tag `vX.Y.Z`       | `X.Y.Z`, `X.Y`, `X`, `latest`                    |
| Tag `vX.Y.Z-<pre>` | `X.Y.Z-<pre>` only                               |

A pre-release moves no other tag. It never becomes `latest`, and it never moves `X.Y` or `X`.

Any other ref stops the `tags` job with `Unsupported ref: <ref>`.

An operator picks one of these tags with `FREENARY_VERSION` in the root `.env`:

```dotenv
FREENARY_VERSION=1.2.0
```

The value is the image tag, with no `v`. The default is `latest`, which exists from the first release on; until then, `dev` and `main` are the only tags. [Updates](/docs/self-hosting/updates) is the operator view.

## The `Release` workflow

`.github/workflows/release.yml`, named **Release**, cuts one version. It has one trigger, `workflow_dispatch`, and one input.

| Input | Required | What it holds |
| --- | --- | --- |
| `version` | yes | The version, without the `v`. For example `1.2.0` or `1.3.0-rc.1`. |

A maintainer runs it by hand:

1. Merge `dev` into `main`, and wait for CI to pass.
2. Open the **Actions** tab of the repository and pick the **Release** workflow.
3. Press **Run workflow**, and select the branch `main`.
4. Type the version in the `version` field, and press **Run workflow** again.

### The three refusals

The first job, `tag`, stops before it writes anything when one of these holds:

| Refusal | Message |
| --- | --- |
| The run started from any branch but `main` | `Releases are cut from main, not from <branch>` |
| The version is not `X.Y.Z` or `X.Y.Z-pre` | `Not a version: <version> (expected X.Y.Z or X.Y.Z-pre)` |
| The tag `v<version>` exists already | `v<version> already exists` |

A version with a `-` in it is a pre-release. The suffix accepts digits, letters and dots.

### What it produces

<Steps>

<Step>

### The tag

The `tag` job creates the annotated tag `v<version>` on the commit the run started from, with the message `Freenary <version>`, and pushes it. The author is `github-actions[bot]`. The job also records the newest earlier `v*` tag, for the release notes.

</Step>

<Step>

### The images

The `images` job calls the `Images` workflow with `ref: refs/tags/v<version>`. That run publishes the version tags of the table above.

</Step>

<Step>

### The GitHub release

The `publish` job creates the release `v<version>`, titled `Freenary <version>`. The notes start with an **Images** section that names both image references and their two platforms, then GitHub appends generated notes from the previous `v*` tag. A pre-release version marks the release as a pre-release.

</Step>

</Steps>

## The merchant data releases

`.github/workflows/generate-data.yml`, named **Generate merchant data**, publishes a second kind of release: the tag `data-<YYYY-MM-DD>` with the asset `merchant-data.tar.gz`. [Transaction categorisation](/docs/development/categorisation#the-weekly-workflow) covers its triggers and its steps.

Those releases use `--latest=false`. A data release is a build input, not a version of Freenary, so it must never become the release a reader sees first on the repository page. An application release carries no such flag, so the newest version is always the `latest` release.
