This page lists the complete persisted model of Freenary. Every field, default, constraint and enum value below comes from the schema files in `packages/db`.

## Where the schema lives

Prisma reads a schema directory, not one file. Four files split the model by domain.

<Files>
  <Folder name="packages/db" defaultOpen>
    <Folder name="prisma" defaultOpen>
      <Folder name="schema" defaultOpen>
        <File name="schema.prisma" />
        <File name="auth.prisma" />
        <File name="budget.prisma" />
        <File name="budget-profile.prisma" />
      </Folder>
      <Folder name="migrations" />
    </Folder>
    <File name="prisma.config.ts" />
  </Folder>
</Files>

`schema.prisma` carries the generator and the datasource and no models.

| Setting | Value |
| --- | --- |
| generator provider | `prisma-client` |
| client output | `../generated`, so `packages/db/prisma/generated` |
| `moduleFormat` | `esm` |
| `runtime` | `bun` |
| `previewFeatures` | `["postgresqlExtensions"]` |
| datasource provider | `postgresql` |
| `extensions` | `[citext]` |
| driver adapter | `PrismaPg` from `@prisma/adapter-pg`, built from `env.DATABASE_URL` |

The datasource block declares no `url`. Two other places supply it. `packages/db/prisma.config.ts` gives it to the Prisma CLI, and `packages/db/src/index.ts` gives it to the driver adapter at runtime. `packages/db` exports the default singleton `prisma`, the `createPrismaClient` factory and the `Prisma` namespace.

`prisma.config.ts` also sets `schema` to `prisma/schema` and `migrations.path` to `prisma/migrations`, and it loads `../../apps/server/.env` with dotenv.

The hierarchy is one chain: user, then bank connection, then bank account, then transaction or holding.

### `BudgetLine` — table `budget_line`

One declared monthly amount. A user's budget lines **are** their budgeting profile. There is no separate profile row.

| Field | Type | Optional | Default | Note |
| --- | --- | --- | --- | --- |
| `id` | `String` `@id` | no | `cuid()` |  |
| `userId` | `String` | no | — |  |
| `label` | `String?` | yes | — | Null when the user gave none; the category name stands in at display time |
| `amount` | `Int` | no | — | Planned amount per month in minor units, always positive |
| `categorySlug` | `String?` | yes | — | A predefined leaf slug, never a group; null when `categoryId` is set |
| `categoryId` | `String?` | yes | — | A `CustomCategory` id |
| `sortOrder` | `Int` | no | `0` |  |
| `createdAt` | `DateTime` | no | `now()` |  |
| `updatedAt` | `DateTime` | no | `@updatedAt` |  |

Indexes `@@index([userId, sortOrder])` and `@@index([categoryId])`. Relations: `user` cascade, and `category CustomCategory?` with **`onDelete: Restrict`**. `Restrict` is safe because `deleteCustomCategory` moves every line that points at the category before it deletes the category.

A line declares a category and nothing else. Its place in the revenues, investments and outgoings flow comes from that category's group through `budgetLineKindOf`, so the two can never disagree.

<Callout type="warn">

No database constraint enforces the exclusive category. The comments say `categorySlug` is null when `categoryId` is set, and the reverse. But Postgres accepts a row with both set, and a row with neither.

</Callout>

## Enums

Postgres holds exactly two enum types.

### `BankConnectionStatus`

`BankConnection.status` uses it. The default is `ACTIVE`.

| Value | Meaning |
| --- | --- |
| `ACTIVE` | The connection imports data. Row creation is the only writer of this value. |
| `EXPIRED` | The consent ran out. **No code writes it.** |
| `ERROR` | The connection failed. **No code writes it.** |

<Callout type="warn">

The interface renders "Reconnect to resume importing" for any status other than `ACTIVE`, and `syncAccounts` skips those rows. But nothing in `packages/api`, `packages/db` or `scripts` ever sets `EXPIRED` or `ERROR`. A manual database update is the only path into either state.

</Callout>

### `BankAccountType`

`BankAccount.type` uses it. The default is `UNKNOWN`. `ProviderAccountType` in `packages/api/src/providers/types.ts` mirrors these member names, so sync writes the value straight through with no mapping.

| Value | Meaning | Holdings? |
| --- | --- | --- |
| `CHECKING` | A current account | no |
| `SAVINGS` | A savings account | no |
| `CARD` | A card account | no |
| `LOAN` | A loan or credit account | no |
| `BROKERAGE` | A securities account | yes |
| `LIFE_INSURANCE` | A life-insurance contract | yes |
| `RETIREMENT` | A retirement plan | yes |
| `EMPLOYEE_SAVINGS` | An employee savings plan | yes |
| `REAL_ESTATE` | A real-estate investment | yes |

### One dropped enum

`BudgetLineKind` was a Postgres type with the values `REVENUE`, `INVESTMENT` and `OUTGOING`. The migration `20260904120000_derive_budget_line_kind` dropped the type together with the column `budget_line.kind`. It survives as a TypeScript union in `packages/api/src/lib/budget-profile.ts`, and `budgetLineKindOfGroup` derives it from a category's group.

### Free-text domains

Three `String` columns on `Transaction` carry a fixed vocabulary that the schema comments define. Postgres does not enforce them.

| Column | Values |
| --- | --- |
| `status` | `BOOK` (the default), `PDNG`, `HOLD`, `SCHD`, `RJCT`, `OTHR` |
| `channel` | `card`, `transfer`, `direct-debit`, `atm`, `fee`, `cheque`, `loan`, `unknown` |
| `transactionPath` | `iban` for direct debits and transfers, `card` for card movements |

The category slugs in `Transaction.category`, `Transaction.resolvedCategory`, `MerchantOverride.category`, `BudgetLine.categorySlug` and `CustomCategory.parentSlug` come from `packages/api/src/lib/taxonomy.ts`. [Transaction categorisation](/docs/development/categorisation#the-taxonomy) lists them.

## Money and precision

| Concern | Representation |
| --- | --- |
| Transaction amount | `Int`, signed minor units of `currency`. Negative is outgoing. Postgres `INTEGER`. |
| Account balance | `balanceMinor Int?` with `balanceAt DateTime?`, minor units of `BankAccount.currency` |
| Balance after a transaction | `balanceAfterTransaction Int?`, minor units |
| Holding valuation | `valuationMinor Int` required, `unrealisedGainMinor Int?`, minor units |
| Holding quantity | `Decimal @db.Decimal(24, 8)` — precision 24, **8 decimal places** |
| Holding unit prices | `unitCost` and `unitValue`, `Decimal? @db.Decimal(24, 6)` — **6 decimal places** |
| Budget line amount | `Int`, minor units, always positive |
| Maximum amount | `MAX_AMOUNT_MINOR_UNITS = 2_147_483_647`, the Postgres `INTEGER` ceiling |
| Currency | A plain `String` ISO 4217 code per row: `Transaction.currency` required, `BankAccount.currency` nullable, `Holding.currency` required |

There is no currency table and no per-user base currency column. A bank provider reports decimal values, and `toMinorUnits(value, precision)` rounds them with `Math.round(value * 10 ** precision)`.

<Callout type="warn">

Two limits follow from that design, and both are real today.

**The stored exchange rate is dead storage.** The Enable Banking adapter maps a rate into `Transaction.exchangeRate`, and `bank-sync.ts` persists it. No code reads the column. There is no conversion, no rate table and no base-currency normalisation.

**Sums cross currencies.** Every aggregation adds `Transaction.amount` over rows without a filter on `currency` and without conversion. A user with a euro account and a pound account gets one number that mixes both.

</Callout>

## Ownership and deletion

Nine models carry their own `userId` column with a foreign key to `user` and `ON DELETE CASCADE`:

`Session`, `Account`, `TwoFactor`, `Passkey`, `BankConnection`, `BankProviderUser`, `MerchantOverride`, `CustomCategory`, `BudgetLine`.

Three models have no user column and inherit ownership through a relation:

| Model         | Path to the user                            |
| ------------- | ------------------------------------------- |
| `BankAccount` | `BankConnection.userId`                     |
| `Transaction` | `BankAccount`, then `BankConnection.userId` |
| `Holding`     | `BankAccount`, then `BankConnection.userId` |

Two models have no owner at all: `Verification` and `RateLimit`.

Prisma emits no row-level security, so every query states the ownership predicate itself. The code uses two shapes:

```ts
// one hop — a bank account, or anything joined to a connection
where: {
  connection: {
    userId;
  }
}

// two hops — a transaction or a holding
where: {
  account: {
    connection: {
      userId;
    }
  }
}
```

Deletion leans on the foreign-key chain. `disconnect` deletes the `bank_connection` row, and the bank accounts, transactions and holdings go with it. `BudgetLine.category` is the one exception: it uses `onDelete: Restrict`, and `deleteCustomCategory` moves the affected lines to the group fallback slug first.

## Onboarding state

There is no onboarding model. Two nullable columns on `User` hold the whole state.

| Column | Written by | Read by |
| --- | --- | --- |
| `country` | `onboarding.completeOnboarding` | `onboarding.getStatus`, and the bank institution list |
| `onboardingCompletedAt` | `onboarding.completeOnboarding` | `onboarding.getStatus`, which returns `completed: onboardingCompletedAt !== null` |

### Commands

| Command | Run from | Literal | Purpose |
| --- | --- | --- | --- |
| `bun run db:migrate --name <snake_case_name>` | `packages/db` | `prisma migrate dev` | Author a migration from a schema edit |
| `bun run db:generate` | repository root or `packages/db` | `prisma generate` | Regenerate the client |
| `bun run db:migrate:deploy` | `packages/db` | `prisma migrate deploy` | Apply pending migrations |
| `bun run db:studio` | repository root or `packages/db` | `prisma studio` | Browse the data |
| `bun run db:push` | repository root or `packages/db` | `prisma db push` | Diff the schema onto a database with no history. Not a setup mechanism. |

`db:migrate:deploy` has no root passthrough script and no Turborepo task. It runs from `packages/db` only. The dev stack runs the same command in its one-shot `bootstrap` service.

### The rule for a pull request

1. Edit the schema file under `packages/db/prisma/schema`.
2. Run `bun run db:migrate --name <descriptive_snake_case>` from `packages/db`. Always pass `--name`.
3. Read the generated SQL. Never hand-write, hand-edit or hand-rename a migration.
4. Never edit or delete a migration that already shipped. Fix forward with a new one.
5. Commit the schema edit and the migration together, in the same pull request.
6. Update this page when you add a model, a column or an enum value.

A schema change also carries a documentation duty. The pages quote enum values verbatim, so a renamed enum member makes a page silently wrong.

The operator side of a migration — when to run it and what breaks when nobody does — is [Update an instance](/docs/self-hosting/updates).
