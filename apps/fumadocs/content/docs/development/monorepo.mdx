Freenary is one Bun workspace repository with three applications and seven packages. The web app renders every screen, the API server exposes one typed procedure set, and the documentation website is a separate application. Turborepo runs the tasks; Prisma owns the database. This page maps the parts and the path a request takes through them.

## Workspaces

The root `package.json` declares two workspace globs, `apps/*` and `packages/*`. Bun pins shared dependency versions in a catalog, so `zod`, `typescript`, `elysia`, `better-auth` and `react` resolve to one version each.

| Workspace | Path | Owns | Depended on by |
| --- | --- | --- | --- |
| `web` | `apps/web` | The web app: routes, screens, message catalogs, the oRPC client | nothing |
| `server` | `apps/server` | The API server: Elysia routes, CORS, the oRPC handlers, log wiring | nothing |
| `fumadocs` | `apps/fumadocs` | The documentation website | nothing |
| `@freenary/api` | `packages/api` | oRPC procedures, the assistant handler and its tools, bank provider adapters, the categorisation pipeline, the category taxonomy | `web`, `server` |
| `@freenary/auth` | `packages/auth` | Better Auth setup, cookie policy, password and rate-limit policy | `@freenary/api`, `server` |
| `@freenary/db` | `packages/db` | The Prisma schema, the migrations, the client singleton | `@freenary/api`, `@freenary/auth`, `server` |
| `@freenary/email` | `packages/email` | The email provider registry and the message templates | `@freenary/auth` |
| `@freenary/env` | `packages/env` | The two environment schemas | `@freenary/api`, `@freenary/auth`, `@freenary/db`, `@freenary/email`, `server`, `web` |
| `@freenary/ui` | `packages/ui` | React primitives | `web` |
| `@freenary/config` | `packages/config` | The shared TypeScript base config | every workspace except `apps/fumadocs`, as a development dependency |

`apps/fumadocs` depends on no workspace package. It is a standalone application.

## A request end to end

This is one real read: the budget page asks for the user's bank accounts.

<Steps>

<Step>
  A component calls the oRPC query utilities. `apps/web/src/utils/orpc.ts`
  builds one `RPCLink` with the URL `${getServerUrl(env.VITE_SERVER_URL)}/rpc`
  and a `fetch` wrapper that sets `credentials: "include"`.
</Step>

<Step>
The browser posts `POST /rpc/budget/getAccounts` with the body `{"json":{}}`. The session cookie `better-auth.session_token` rides along. No procedure answers a `GET`.
</Step>

<Step>
Elysia routes the request. `apps/server/src/index.ts` declares `.all("/rpc*", …, { parse: "none" })`, so Elysia does not read the body. The `cors()` plugin admits one origin, `env.CORS_ORIGIN`.
</Step>

<Step>
The route handler calls `createContext` from `packages/api/src/context.ts`. It returns exactly `{ auth: null, headers, session }`.
</Step>

<Step>
  `createContext` resolves the session with `auth.api.getSession({headers})`.
  Better Auth reads the cookie and loads the `session` row. With no cookie the
  session is `null`.
</Step>

<Step>
  `RPCHandler` matches the procedure and runs the middleware.
  `protectedProcedure` in `packages/api/src/index.ts` throws
  `ORPCError("UNAUTHORIZED")` when `context.session?.user` is absent. The caller
  gets HTTP 401.
</Step>

<Step>
The handler in `packages/api/src/routers/budget.ts` queries Prisma. Ownership is an explicit predicate, `where: { account: { connection: { userId } } }`, because Prisma emits no row-level security.
</Step>

<Step>
`RPCHandler` wraps the return value as `{"json": …, "meta": […]}` with status 200. When the handler produces no response, the route falls back to `new Response("Not Found", { status: 404 })`.
</Step>

</Steps>

A server-rendered page takes a shorter path. The browser requests a route path, and `apps/web/src/server.ts` wraps the TanStack Start server entry with `paraglideMiddleware`, then appends `Vary: Accept-Language, Cookie` to the response. TanStack Start renders the matched route from the generated route tree. During that render `getServerUrl` in `apps/web/src/lib/server-url.ts` prefers `SERVER_URL`, so the server-side fetch reaches the API server over the container network instead of `localhost`.

## The assistant

The assistant is the one surface that does not answer over oRPC. Every procedure in `packages/api` is unary, and the web client is a plain `RPCLink`, so no procedure can hand back tokens as they arrive. The token stream is a raw Elysia route; everything the assistant reads still goes through the procedures, so an answer and a chart cannot disagree.

`packages/api/src/assistant/` holds seven files:

  </Folder>

`packages/api/src/routers/assistant.ts` holds the three procedures beside them. [Procedure reference](/docs/integrations/procedures) covers those, and [API](/docs/integrations/api#the-assistant-stream) covers the route below.

`apps/server` stays glue. `apps/server/src/index.ts` declares `.post("/ai/chat", …, { parse: "none" })` and calls `handleAssistantChat` from `@freenary/api/assistant/handler`. The route sits after `evlog()` and after the `.derive` that runs `identifyUser`, so it inherits the request's wide event and the identified user. `parse: "none"` keeps Elysia away from the body, for the same reason `/rpc*` sets it.

`prompt.ts` builds the system prompt from the locale, today's date, the transaction date range and whether any bank account is connected. The prompt forbids a figure that did not come from a tool, orders the model to refuse a period outside the data range instead of extrapolation, states that tool amounts are already decimal figures in the currency each result names and must not be rescaled, tells it to name a category slug naturally in the reader's language, and ends on "information and arithmetic, never regulated financial advice". It then appends the chart section that `ui.ts` generates.

### The chart library

`ui.ts` defines five components with `defineComponent` from `@openuidev/lang-core`: `Card`, the root, then `Stat`, `BarChart`, `LineChart` and `DonutChart`. Each definition is a name, a description and a Zod object whose key order is the positional argument order in [OpenUI Lang](https://www.openui.com/). `createLibrary` turns them into a library, and `library.prompt()` writes the syntax rules, the component signatures and two worked examples into the system prompt. The generation runs once per process. `lang-core` imports no React, so the API server stays free of it.

The prompt is generated with `toolCalls: false` and `bindings: false`. OpenUI Lang can call a tool provider from the browser and hold reactive state; the assistant uses neither, so a program is a literal snapshot of the figures the model already read.

`apps/web/src/components/assistant/assistant-ui-library.tsx` spreads each definition from `@freenary/api/assistant/ui` into `defineComponent` from `@openuidev/react-lang` and attaches the renderer. Its renderer table `satisfies Record<keyof typeof ASSISTANT_UI, …>`, so a definition added in `ui.ts` fails the web type-check until it has a renderer. The charts render through `ChartContainer` from `packages/ui` and recharts, take their colours from `CHART_COLOR_VARS` in order, and format every amount as the decimal the tool returned, through `formatDecimalCurrency` in `lib/budget/format-currency.ts`. A value missing from a series is a gap, never a zero.

`apps/web/src/lib/assistant/answer-segments.ts` splits a text part into markdown and fenced `openui-lang` programs; `assistant-message.tsx` hands the first to the markdown renderer and the second to `assistant-chart.tsx`, which wraps `<Renderer>`. A fence still open at the end of the text is a chart in progress. Any other fence stays markdown. The parser drops a child it cannot validate and records why, so once the fence closed `assistant-chart.tsx` treats a recorded error, an empty root or no root as a broken chart and prints the failure line in its place.

<Callout type="info">
  `@openuidev/react-lang` auto-mounts a floating **Open OpenUI Inspect** button
  in development, loaded from a CDN. It is dead code in a production build.
</Callout>

### Four rules inside the handler

**The tools call procedures, not Prisma.** `assistantTools` takes a server-side router client, `createRouterClient(appRouter, { context })`, and each tool is a description, a Zod input schema and one procedure call. A second implementation of "outgoing transactions in a period" would agree with the charts on the day somebody wrote it, then drift, so an answer and a chart could disagree. A procedure call also carries the `protectedProcedure` session guard, which a tool therefore cannot forget.

**The stream route ignores the posted transcript, and `assistant.saveTurn` is the second writer.** The browser posts the whole transcript on every question. The route reads the last message only, which must be a text-only user turn, and rebuilds the model's context from the `conversation_message` rows. Those rows have two writers: the stream route writes the turn a server model produced, and `assistant.saveTurn` writes the turn the browser posts when a browser model answered, on every instance. The server cannot verify that a browser model wrote a posted turn. It checks the part schema, the size caps and the shared rate limit that [Procedure reference](/docs/integrations/procedures#assistantsaveturn) lists, and nothing more, so a session holder can write any text into the assistant rows of their own conversation, and the next question to the server model replays it. The reach of that is one user's own context at the operator's endpoint; [Security](/docs/self-hosting/security#the-assistant-sends-data-to-the-endpoint-you-configure) records the operator side.

**An answer chains at most six lookup rounds.** `handler.ts` passes `stopWhen: stepCountIs(MAX_STEPS)` with `MAX_STEPS = 6`. After the sixth round the model must conclude from what it already read.

**The wide event closes before the body does.** `createAILogger(log)` from `evlog/ai` wraps the model, so token counts and per-tool timings reach the request's wide event. The Elysia event closes when the handler returns its `Response`, which happens before the body finishes streaming. Nothing measured after the last token is on that event.

[Data model](/docs/development/data-model#assistant-conversations) holds the two tables and the rules that decide what a turn stores.

### The model picker

`assistant.getConversation` reports `serverModel`: the `AI_MODEL` id when both `AI_BASE_URL` and `AI_MODEL` are set, and `null` otherwise. `assistantModelId()` in `packages/api/src/assistant/provider.ts` computes it, and `handleAssistantChat` answers 503 `unconfigured` for the `null` case. The reader picks the model inside the conversation, between that server model and the `@mlc-ai/web-llm` builds their browser can run, and the web app runs the same loop in the browser for a browser model, on weights it downloads from the Hugging Face CDN and WebGPU executes. `apps/web/src/lib/assistant/model-choice.ts` holds the choice: `SERVER_MODEL`, the `localStorage` key `freenary.assistant.model`, `useRememberedModel`, `rememberModel`, and `resolveModelChoice`, which drops a remembered `server` choice on an instance that lost its endpoint. [Assistant](/docs/self-hosting/assistant#the-browser-model) is the operator view, and [The assistant](/docs/guides/assistant#choose-a-model) is the reader's.

`models.ts` offers only the model families that follow the Hermes and Qwen `<tool_call>` text protocol: twelve entries across Qwen3, Qwen3.5, Qwen2.5, Hermes 3 and Llama 3. Each carries the `vram_required_MB` of its build from WebLLM's prebuilt list plus the KV cache the longer window adds, and the model list sorts them by that figure. An id ends `-q4f16_1-MLC` on a GPU that reports `shader-f16`, and `-q4f32_1-MLC` otherwise. The context window is 8192 tokens against WebLLM's 4096 default; `history.ts` drops the oldest turns of a transcript, as question-and-answer pairs, until the prompt fits it, and an overflow that still happens tells the reader to start a new conversation. Qwen3 loads with `enable_thinking: false`.

`tool-protocol.ts` writes the seven tool signatures into the system prompt as JSON inside a `<tools>` block. The model answers with `<tool_call>{"name","arguments"}</tool_call>`, and each result returns as a user turn that holds `<tool_response>{"name","content"}</tool_response>`. A streaming `ToolCallParser` splits prose, `<think>` reasoning and tool calls. WebLLM carries a native `tools` field, and this code does not use it: that field accepts five Hermes builds only, refuses a system prompt beside the tools, and forces the whole answer through a JSON grammar, so a model could call a tool but never write the sentence after it.

`engine.ts` keeps one `WebWorkerMLCEngine` per page in `worker.ts`, and exports `loadBrowserModel`, `browserModelCatalog`, `useWebGpuSupport` and the `useBrowserModel()` store with its four states `idle`, `loading`, `ready` and `error`. It remembers no model itself: the choice lives in `model-choice.ts`. `transport.ts` is an AI SDK `ChatTransport`: it runs `streamText` with `assistantSystemPrompt`, `assistantTools(client)` over the web oRPC client and `stepCountIs(MAX_STEPS)`, then writes the finished turn through `client.assistant.saveTurn`. `turn.ts` holds the rules both paths share, so a browser answer stores exactly what a server answer stores.

### The execution trace

A `UIMessage` from the SDK is a flat list of parts: `step-start` markers, `reasoning`, `tool-<name>` and `text`. `apps/web/src/lib/assistant/execution.ts` folds that list into steps, one per model call, and reads a tool's five states off its SDK state: `input-streaming` is preparing, `input-available` is running, `output-available` is done, `output-error` failed, and a call still waiting once the stream ended is cancelled. `activityOf` names what the live answer does right now for the status line.

The stream carries no clock, so `use-execution-timings.ts` measures on the client: a part's timer starts the first render it appears in and stops the first render it is settled in, and the turn's own timer starts when the question was sent. A replayed transcript never started a timer, so a stored answer shows no durations rather than invented ones.

The model's reasoning parts are stored and replayed to the model, but never rendered: `assistant-trace.tsx` shows **Thought** with its duration on the line under the step. The timeline is one column: a step that made one lookup renders as that lookup's row (`tool.tsx` draws no card and puts its chevron last, so every row's text starts at the rail), and the registry's `reasoning.tsx` was dropped rather than nested under a step. `assistant-message.tsx` is memoised and the chat passes settled rows constant props, so a streamed chunk re-renders the live answer alone; without that, every chart on the screen re-rendered on every chunk and the page stalled.

`apps/web/src/routes/_auth/index.tsx` renders the chat, so Home is the assistant. [The assistant](/docs/guides/assistant) is the reader's view.

## The runtime

Bun runs everything. The root `package.json` pins `bun@1.3.14` in `packageManager`, and both production images start from `oven/bun:1`.

| Application | Framework | Entry file | Build command | Output |
| --- | --- | --- | --- | --- |
| `apps/server` | Elysia | `apps/server/src/index.ts` | `tsdown` | `apps/server/dist/index.mjs`, ESM |
| `apps/web` | TanStack Start with Nitro, preset `bun` | `apps/web/src/server.ts` | `vite build` | `apps/web/.output/server/index.mjs` |
| `apps/fumadocs` | TanStack Start with Nitro, preset `vercel` | route files under `apps/fumadocs/src/routes` | `vite build` | Nitro Vercel output, prerender turned on |

`apps/server/tsdown.config.ts` sets `clean: true`, `format: "esm"` and `deps.alwaysBundle: [/@freenary\/.*/u]`, so the server bundle carries the workspace packages inside it. The web app does the opposite: its runner image copies the whole `/app` tree, because the SSR chunks load workspace dependencies at runtime.

The API server listens on `env.PORT`, default `3000`. The web dev server listens on `3001`. The documentation website dev server listens on `4000`, because the `dev` script passes `vite dev --port=4000`.

## Configuration and validation

`packages/env` is the one seam for configuration. It holds two schemas and nothing else.

| File | Key | Reader | Notes |
| --- | --- | --- | --- |
| `packages/env/src/server.ts` | `server` | `import { env } from "@freenary/env/server"` | 36 variables, `runtimeEnv: process.env`, `emptyStringAsUndefined: true`, `skipValidation: !!process.env.SKIP_ENV_VALIDATION` |
| `packages/env/src/web.ts` | `client`, `clientPrefix: "VITE_"` | `import { env } from "@freenary/env/web"` | `VITE_SERVER_URL`, default `http://localhost:3000` |

Both use `@t3-oss/env-core` with Zod. The rule is simple: add the Zod schema here, then read `env`. No other file reads `process.env`.

Three of those 36 variables reach one reader only. `packages/api/src/assistant/provider.ts` imports `env` from `@freenary/env/server` and builds the model client from them, inside the API server process. `apps/web` reads none of them, and `packages/env/src/web.ts` holds no `VITE_AI_*` key. The browser learns only the result: `serverModel` from `assistant.getConversation` names the model of the instance, or reports that it has none.

| Variable | Read by | What the reader does with it |
| --- | --- | --- |
| `AI_BASE_URL` | `packages/api/src/assistant/provider.ts`, in the API server process | The `baseURL` of the `@ai-sdk/openai-compatible` client |
| `AI_API_KEY` | The same file and process | The `apiKey` of that client |
| `AI_MODEL` | The same file and process | The model id `provider.chatModel()` asks for |

All three are optional, and none has a default. [Configure the assistant](/docs/self-hosting/assistant) is the operator view: which endpoints work, what the model must support, and what a question sends to it.

Eight places break that rule today. Two of them are legitimate.

| Place | Variable | Why |
| --- | --- | --- |
| `packages/env/src/server.ts` | `PORT`, `SKIP_ENV_VALIDATION` | The schema itself. `PORT` is digits-only so the raw string can go into the `BETTER_AUTH_URL` default before coercion. |
| `apps/server/src/index.ts` | `NODE_ENV` | Picks the evlog drain before `env` is in scope for that expression |
| `apps/web/src/lib/server-url.ts` | `SERVER_URL` | Server-only value with no `VITE_` prefix, read off `globalThis.process` |
| `packages/api/src/categorisation/verify.ts` | `DICTIONARY_PUBLIC_KEY` | **Not in the schema.** It skips validation and startup failure. See [Transaction categorisation](/docs/development/categorisation). |
| `packages/db/prisma.config.ts` | `DATABASE_URL` | The Prisma CLI config. A schema read would abort config load, and `postinstall` must work with no `.env` file. |
| `packages/api/scripts/download-data.ts` | `GITHUB_REPOSITORY`, `GITHUB_TOKEN` | Build-time script, outside the server process |
| `scripts/dev.ts` | `FREENARY_SLUG` | Development wrapper, outside the server process |
| `apps/fumadocs/src/routes/api.chat.ts` | `OPENROUTER_API_KEY`, `OPENROUTER_MODEL` | The documentation website does not depend on `@freenary/env` |

The operator view of every server variable is [Configuration](/docs/self-hosting/configuration).

## Boundaries

Three boundaries hold the code apart. Break one and the failure is quiet, not loud.

**`packages/api` imports the data and identity packages only.** Its dependencies are `@freenary/auth`, `@freenary/db` and `@freenary/env`. It must not import `@freenary/ui`, `apps/web`, or the compiled message modules. `elysia` is a development dependency for one type: `packages/api/src/context.ts` is the only file that touches the server framework, so a framework change stops there.

**`apps/web` imports the router type, never the implementation.** `apps/web/src/utils/orpc.ts` imports `AppRouter` as a type and calls the procedures over HTTP.

**Responses carry slugs and enum members, never display strings.** The web app carries translations. The API server does not. A human-readable `label` in a response is English text. The client cannot translate it. So the API sends the stable key — `"daily-living"`, `"ACTIVE"` — and the web app maps that key to a message. Text that comes from the user, the bank or the bank provider is data, not interface copy, and passes through as-is.

Interface strings live in `apps/web/messages/en.json` and `apps/web/messages/fr.json`. A key in one catalog and absent from the other compiles with no error. Both catalogs change in the same commit.

Each package states its own rules next to its code:

- [`packages/api/AGENTS.md`](https://github.com/suiramdev/freenary/blob/main/packages/api/AGENTS.md)
- [`packages/db/AGENTS.md`](https://github.com/suiramdev/freenary/blob/main/packages/db/AGENTS.md)
