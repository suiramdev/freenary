Categorisation turns a bank descriptor into a category slug. The code lives in `packages/api/src/categorisation`, and the offline scripts live in `packages/api/scripts`.

The pipeline is a batch pass over stored rows. It never runs when the web app reads a transaction. Two procedures in `packages/api/src/routers/budget.ts` drive it:

| Caller | When | What it does first |
| --- | --- | --- |
| `budget.syncAccounts` | After a sync imported transactions | Runs `matchInternalTransfers`, then categorises |
| `budget.recategorise` | The reader asks for a fresh pass | Runs `clearResolutions`, then categorises |

`categoriseUncategorised` selects the rows where `resolvedCategory` is null, `categoryOverride` is false and `isInternalTransfer` is false. Every stage writes the same four columns on a hit: `resolvedCategory`, `resolutionStage`, `resolutionConfidence` and `intermediaryName`. A failed row update does not stop the pass. [Data model](/docs/contributing/data-model#what-the-categorisation-pipeline-writes) owns those column names.

<Callout type="info">

A second cascade answers at read time and stores nothing. The procedure `budget.getTransactions` calls `effectiveCategory`, which prefers `Transaction.category`. It then falls back to `deriveCategory` in `packages/api/src/lib/mcc-categories.ts`. That function re-runs the merchant category code, then income by sign, then the flat keyword tables. It ends at `uncategorised` rather than an abstention, and it has no country to dispatch on. So it can disagree with the pipeline.

</Callout>

## The stages

The function `categoriseBatch(transactions, countries)` loads the dictionary and the model once with `Promise.all`. It walks the batch in order, then unloads both in a `finally` block. Nothing escapes `categoriseTransaction`: any error becomes the unknown result.

`ResolutionStage` holds exactly `channel`, `user-override`, `dictionary`, `mcc`, `rules`, `model`, `cloud` and `none`. `ResolutionBand` holds `auto`, `suggest` and `unknown`.

| # | Stage | Condition | Confidence | Stage value |
| --- | --- | --- | --- | --- |
| 0 | Merchant key derivation | Always, at sync rather than in the pipeline | — | — |
| 1 | Channel short-circuit | `channel` is `atm`, `cheque` or `fee` | `0.9`, band `auto` | `channel` |
| 2 | User override | A `MerchantOverride` row exists for the pair of user and merchant key | `1`, band `auto` | `user-override` |
| 3 | Shared dictionary | An exact hit on the merchant key, or on the key minus a trailing qualifier word | `0.85`, band `auto` | `dictionary` |
| 4a | Merchant category code | `merchantCategoryCode` resolves | `0.8` | `mcc` |
| 4b | Keyword rules | The first hit across four ordered lookups | `0.75` | `rules` |
| 5 | Local classifier | `predict()` answers at or above `MODEL_ACCEPT_THRESHOLD`, which is `0.7` | The score itself. Band `auto` at `0.85` and above, else `suggest` | `model` |
| 6 | Cloud tail | Never. The stage holds a comment and no code | — | `cloud`, which nothing writes |
| 7 | Unknown | The fallthrough | `0`, band `unknown` | `none` |

Stages 2 and 3 are skipped when the merchant key is empty. Stages 4 and 5 still run.

<Steps>

<Step>

### Stage 0 — the merchant key

`deriveMerchantKey` runs inside the sync, and `upsertTransaction` persists `merchantKey`, `normalisedDescriptor`, `channel`, `transactionPath` and `intermediaryName`. Two paths exist.

The **IBAN path** takes a creditor IBAN when the family code is `ICDT`, `PMNT`, `RCDT` or `RDDT`. It also takes one when no family code exists and the raw descriptor does not look like a card movement. The key is the trimmed upper-case IBAN.

The **card path** normalises the parsed payee text. With a payment service provider in the middle, it takes the sub-merchant text instead. It then strips trailing place tokens. Any throw returns an empty key with `channel: "unknown"` and the card path.

Normalisation folds the `oe` and `ae` ligatures, strips combining marks and apostrophes, then lowercases. It splits on non-alphanumerics, then drops digit-bearing tokens and 91 noise tokens. The same function normalises a bank descriptor and a dictionary name, which is what makes the two comparable.

</Step>

<Step>

### Stage 1 — channel short-circuit

One constant table of three entries.

| Channel  | Category          |
| -------- | ----------------- |
| `atm`    | `cash-withdrawal` |
| `cheque` | `uncategorised`   |
| `fee`    | `bank-fees`       |

The channel value seeds from the ISO 20022 family code. A verb prefix overwrites it only when it is still `unknown`.

</Step>

<Step>

### Stage 2 — user override

`lookupUserOverride` runs a `findUnique` on the unique index of `MerchantOverride`. A database error returns `null` rather than an exception. A hit carries the stored merchant name.

</Step>

<Step>

### Stage 3 — shared dictionary

An exact-match table. The relaxation sits in the key, not in the lookup. The helper `merchantKeyCandidates` yields the key, then the key minus one trailing qualifier token at a time. It stops at the first non-qualifier tail, or when the candidate falls below the minimum length.

The default qualifier layer is `internet`, `mobile` and `telecom`. The French layer adds `abonnement`, `electricite`, `energie`, `energies`, `fibre`, `forfait`, `france` and `gaz`.

</Step>

<Step>

### Stage 4 — the deterministic layer

**4a, the merchant category code.** Three ranges answer first: `3000-3299` gives `flights`, `3300-3499` gives `other-travel`, and `3500-3999` gives `accommodation`. A flat table of 221 keys answers after them. The stage runs no direction check. A code on a credit therefore lands in the category of the merchant, as a refund.

**4b, the keyword rules**, in this order:

1. The bank code against the `bankCode` table.
2. The counterparty name against the `counterparty` table.
3. The normalised descriptor against the `counterparty` table.
4. The normalised descriptor against the `bankCode` table.

Every candidate passes `accept()`, which rejects a non-income category on a positive amount. The tables concatenate the country layer before the default layer once, at module load. Only `FR` is registered: `default.ts` holds 17 rows and `fr.ts` holds 7. Each pattern is wrapped in lookarounds by `tokens()`, so it matches whole tokens only.

</Step>

<Step>

### Stage 5 — the local classifier

`predict(normalisedDescriptor, country)` returns `null` with no weights file and with an empty descriptor. The classifier abstains below `CONFIDENCE_THRESHOLD = 0.5`, and the pipeline then discards anything below `MODEL_ACCEPT_THRESHOLD = 0.7`.

</Step>

<Step>

### Stage 6 — the cloud tail

**Stage 6 runs no code.** Three comment lines mark its place in `resolve.ts`, and execution falls through. `ResolutionStage` declares `cloud` and `CategoriseInput` declares `allowCloudInference`. The one producer sets that flag to `false`, and no code reads it.

</Step>

<Step>

### Stage 7 — unknown

`UNKNOWN_RESULT` is `{ band: "unknown", category: null, confidence: 0, intermediaryName: null, merchantName: null, stage: "none" }`.

</Step>

</Steps>

### Two passes beside the pipeline

| Pass | File | What it writes |
| --- | --- | --- |
| Internal transfers | `internal-transfer.ts` | Pairs an outgoing and an incoming transaction of equal absolute amount and the same currency, on two accounts of one user, inside 24 hours. It then sets `isInternalTransfer: true`, `resolvedCategory: "internal-transfer"`, `resolutionStage: "channel"` and `resolutionConfidence: 0.95` |
| Recurrence | `recurrence.ts` | Nothing. It groups outgoing transactions by merchant key. It then reads a cadence, a recurrence type, a confidence level and a month-by-month split. The file holds no write, and each request recomputes the answer. [Recurrence detection](#recurrence-detection) holds the rules |

The internal-transfer pass includes rows that already carry a category, and it returns `0` on any throw.

<Callout type="info">

**Dead code, stated as a fact about the current tree.** `internal-transfer.ts` selects `BankAccount.identificationHash` and never uses it. The pairing reads amount, currency and date alone. The schema comment calls that column a cross-account matching key, and no code matches on it.

</Callout>

## Deterministic versus trained

| Part | Deterministic |
| --- | --- |
| Merchant key derivation, normalisation, channel detection, intermediary detection | yes, pure functions over the transaction and static tables |
| Stage 1, the channel short-circuit | yes, a three-entry constant |
| Stage 2, the user override | yes, one `findUnique` on a unique index |
| Stage 3, the dictionary | yes, an exact `Map.get` on a pre-built artifact |
| Stage 4, the code and the keyword tables | yes, range checks and regular expressions |
| The internal-transfer pass | yes, amount, currency and date arithmetic |
| Stage 5, the classifier | no. A trained model answers |

<Callout type="warn">

**No large language model touches categorisation.** The one model in the pipeline is a multinomial linear classifier over hashed character n-grams. It loads a JSON weights file from disk and scores in process. It opens no socket, calls no endpoint and sends no descriptor anywhere.

The header comment of `resolve.ts` calls stage 5 a stub. That comment is wrong. `predict()` is a complete implementation and stage 5 calls it. Stage 6 is the stub. The assistant is a separate surface: nothing under `categorisation/` imports from `assistant/`, and nothing under `assistant/` imports from `categorisation/`.

</Callout>

The header of `resolve.ts` states the contract that does hold. Stages 1 to 4 are deterministic: the same transaction data always gives the same category. No model is involved, and the classifier sees what those stages leave undecided.

## Recurrence detection

`recurrence.ts` reads a cadence out of the stored transactions. It is a pure read: it holds no write, and it never throws. `detectRecurring` returns empty aggregates on a database error. [Budget](/docs/guides/budget) is the reader view of the result. The procedure that serves that view is [`budget.getRecurring`](/docs/integrations/procedures#budgetgetrecurring).

### What a group is

`recurringInWindow(transactions, window)` groups the transactions by `merchantKey`. The read behind it takes outgoing rows alone, and it drops an internal transfer. The window is enforced in the grouping, not in the query. A row with no merchant key joins no group, and a group of fewer than two transactions is dropped.

The detector sorts each group by date. It then measures the interval in days between consecutive transactions. The median of those intervals is the cadence, and `nextExpected` is the last date plus that median.

### The frequency bands

The median interval lands in one band. Each band sets its own minimum of occurrences.

| Frequency   | Median interval                          | Minimum occurrences |
| ----------- | ---------------------------------------- | ------------------- |
| `weekly`    | 5 to 9 days                              | 4                   |
| `monthly`   | 25 to 35 days                            | 3                   |
| `quarterly` | 80 to 100 days                           | 2                   |
| `annual`    | 340 to 395 days                          | 2                   |
| `irregular` | 10 to 400 days, outside every band above | 4                   |

A median interval outside every named band falls back to `irregular`. A group that misses the minimum of its band gives no result at all.

### Dispersion

Both spreads are a relative median absolute deviation: `median(|v − median(v)|) / median(v)`. The value is `0` when the median is `0`. A ratio, rather than cents or days, makes an amount and an interval comparable against one threshold.

| Signal           | Measured over                                  |
| ---------------- | ---------------------------------------------- |
| `amountSpread`   | The absolute amounts of the group              |
| `intervalSpread` | The intervals between consecutive transactions |

The file exports three thresholds.

| Name | Value | Meaning |
| --- | --- | --- |
| `STABLE_AMOUNT_SPREAD` | `0.05` | At or below it, the charge repeats at the same price |
| `VARIABLE_AMOUNT_SPREAD` | `0.25` | Above it, the reader sets the price rather than a contract |
| `REGULAR_INTERVAL_SPREAD` | `0.2` | At or below it, the cadence holds a schedule |

### The classification

`classifyRecurrence({ amountSpread, frequency, intervalSpread, occurrences })` is pure and exported. It reads those four signals and no transaction list. It returns one `kind` and one `confidence`.

`kind` is `fixed` when all three conditions hold:

1. The frequency is not `irregular`.
2. `intervalSpread` is at most `REGULAR_INTERVAL_SPREAD`.
3. `amountSpread` is at most `VARIABLE_AMOUNT_SPREAD`.

Every other group is `behavioral`. The confidence follows from the kind:

| `kind` | Condition | `confidence` |
| --- | --- | --- |
| `fixed` | `amountSpread` at most `STABLE_AMOUNT_SPREAD`, and 3 occurrences or more | `confirmed` |
| `fixed` | Any other fixed group | `likely` |
| `behavioral` | Always | `pattern` |

<Callout type="info">

**Neither an exact date nor an exact amount is needed.** A bank moves its processing date, and a utility bill moves its amount. A group still reads as `fixed` while both spreads stay inside their thresholds. `REGULAR_INTERVAL_SPREAD` sets how far the date can move, and `VARIABLE_AMOUNT_SPREAD` sets how far the amount can move.

</Callout>

### One read, two aggregates

`detectRecurring(userId, window)` does one transaction read and returns both aggregates. The field `expenses` holds the detected patterns, biggest typical amount first. The field `months` holds the month-by-month split.

`recurringMonthsInWindow(transactions, window, expenses)` attributes each in-window outgoing transaction to one of three totals. The key is `YYYY-MM`, with a 1-based calendar month.

| Total | What it collects |
| --- | --- |
| `fixedMinor` | A merchant key the detector classified as `fixed` |
| `behavioralMinor` | A merchant key the detector classified as `behavioral` |
| `discretionaryMinor` | Everything else |

The third total is the fallback. A transaction with no `merchantKey`, or one that no detected pattern claims, is discretionary. The split takes the detected expenses rather than a second detection pass, so the two aggregates always agree. It returns the months it saw, and a caller that wants a fixed span fills the gaps itself.

### The two windows

| Helper | Window | What it means |
| --- | --- | --- |
| `cadenceWindow(from, to)` | The period widened by one year on each side | A cadence belongs to the merchant, not to where the reader stands, so the same rent never reads fixed in one month and variable in the month before it |
| `trailingYear(to)` | The year that ends at `to` | The window a forward-looking commitment list means |

`detectRecurringExpenses(userId, window)` keeps its old signature and its old behaviour. It is a projection of `detectRecurring` on the `expenses` field.

## The taxonomy

`packages/api/src/lib/taxonomy.ts` declares the taxonomy once, in code. The database declares no part of the predefined set.

| Thing | Symbol | Count |
| --- | --- | --- |
| Category groups, in flow order | `CATEGORY_GROUPS` | 16 |
| Category slugs, income included | `SPENDING_CATEGORIES` | 75 |
| Category to group | `CATEGORY_GROUP_OF` | exhaustive |
| Group colours | `CATEGORY_COLOR_VALUES` | 7 |
| Group icons | `CATEGORY_ICON_NAMES` | 18 |
| Group fallbacks | `CATEGORY_GROUP_FALLBACKS` | one `other-*` slug per group |
| Legacy slugs | `LEGACY_CATEGORY_SLUGS` | 17 pre-hierarchy spellings |

The 16 groups are `income`, `investments`, `housing`, `utilities`, `daily-living`, `transport`, `travel` and `leisure`. The rest are `shopping`, `subscriptions`, `health`, `education`, `financial`, `taxes`, `transfers` and `other`.

**The hierarchy holds exactly two levels.** A group holds leaves and a leaf holds nothing. A colour and an icon belong to the group, so `categoryColor` and `categoryIcon` resolve through it.

**A signal maps to the most precise category it supports, and no further.** A merchant category code for a supermarket gives `groceries`. A bank code that proves housing alone gives `other-housing`, the group fallback. The pipeline invents no precision the signal does not carry.

`LEGACY_CATEGORY_SLUGS` decodes a pre-hierarchy spelling, so a stored row and an old artifact still resolve. A reader cannot add or rename a predefined category. The array `SPENDING_CATEGORIES` is `as const`, and both the update procedure and the transaction filter accept its enum alone. Custom categories exist for budget lines, under the key space `custom:<id>`. [Categories](/docs/guides/categories) is the reader view.

## User corrections

A correction of the reader is permanent, and it asks for no reconciliation.

`budget.updateTransactionCategory` runs one database transaction:

1. It validates the input against `z.enum(SPENDING_CATEGORIES).nullable()`. A `null` clears the choice.
2. It sets `Transaction.category`, and `categoryOverride` to the truth of a non-null category.
3. With a merchant key on the row, it upserts a `MerchantOverride` row, or deletes it for a `null` category.
4. It propagates the value to the sibling transactions with the same merchant key and no override of their own.

`upsertUserOverride` and `deleteUserOverride` swallow every error, so a failure there cannot break a sync. The override becomes stage 2 and outranks stages 3 to 7.

<Callout type="warn">

Stage 1 runs **before** the override. A transaction whose channel is `atm`, `cheque` or `fee` short-circuits at stage 1. The pipeline never reads the override for it. The read-time value still honours `Transaction.category`.

One more asymmetry: stage 3 relaxes the merchant key with the qualifier list and the stage 2 lookup does not. An override recorded on `free mobile` does not fire for `free mobile internet`, and the dictionary does.

</Callout>

## The merchant dictionary

The artifact is `packages/api/data/merchants.jsonl.gz`, gzipped JSONL, one merchant per line.

| Field | What it holds |
| --- | --- |
| `id` | The merchant id. The build sorts the rows by it |
| `name` | The display name |
| `normalisedName` | The match key |
| `category` | A category slug, or `null`. The loader drops a null row |
| `domains` | The domains the build collected for the merchant |
| `source` | The provenance of the row, such as the Name Suggestion Index |
| `aliases` | Each alias with its normalised form |
| `countries` | The country scope. It is optional, because an artifact built before the scope existed carries none |

`dictionary.ts` streams the file into a module map with a reference count. The keys are `normalisedName` plus every `normalisedAlias` that no other row took. It drops a row with a null category. It also drops a row outside the country scope of the batch, where an empty `countries` list means worldwide. A missing file warns once and leaves an empty map, so stage 3 becomes a permanent miss.

### The build

`build-merchant-dictionary.ts` fetches a pinned Name Suggestion Index tarball, version `8.0.20260729`, and runs these passes:

| Pass | What it does |
| --- | --- |
| 1 | Collects the raw candidates, and maps an index path to an OpenStreetMap tag and then to a category |
| 2 | Drops place-only names. **A permanent no-op**: `isEntirelyPlaceName` returns `false` for every input, so the pass drops nothing and still logs a count of zero |
| 3 | Resolves `normalisedName` collisions by category priority, elects one primary name, and unions the aliases, the domains and the country scopes |
| 3b | Merges the Wikidata aliases and domains, with no category. A missing input file warns and skips |
| 3c | Enriches a still-uncategorised French-linked merchant through the SIRENE register, inside a 15-minute budget. A failure warns and continues |
| 4 | Merges the curated supplement of 54 hand-written entries, which wins every collision |

Place-token stripping still happens at runtime, on the tail of the merchant key. Pass 2 is the build-time filter, and it is inert.

Rows sort by `id` for byte-stable diffs, then compress at gzip level 9. **One artifact covers every country**, and each consumer filters `countries` in memory. A transient failure with an artifact already on disk warns and exits `0`. So a stale dictionary can survive a green build.

| Source | Endpoint or version |
| --- | --- |
| Name Suggestion Index | `name-suggestion-index@8.0.20260729` from the npm registry |
| Wikidata | `data/wikidata-brands.json`, built by `fetch-wikidata-brands.ts` |
| SIRENE company register | `https://recherche-entreprises.api.gouv.fr/search` |
| Curated supplement | `packages/api/scripts/lib/curated-merchants.ts` |

### The scripts

Run each one from `packages/api`.

| Script | Literal command | Writes |
| --- | --- | --- |
| `build:data` | `bun scripts/download-data.ts \|\| bun run build:data:generate` | The released artifacts, or the rebuilt ones |
| `build:data:generate` | `generate-place-tokens.ts && fetch-wikidata-brands.ts && build-merchant-dictionary.ts` | The same artifacts, from the upstream sources |
| `build:places` | `generate-place-tokens.ts` | `data/place-tokens.json` |
| `generate:key` | `generate-signing-key.ts` | `data/dictionary.key`, mode `0600`, and the public key on standard output |
| `train:model` | `train-model.ts` | `data/model-weights.json`, when the gate passes |

The root passthrough is `bun run build:data`, which Turborepo marks uncached. The script `download-data.ts` deletes any local `model-weights.json` before it downloads. A failed download plus a local rebuild can therefore never pair weights with a dictionary they do not match. It resolves the repository from `GITHUB_REPOSITORY`, then from the `origin` remote, then from the literal `suiramdev/freenary`.

## The dictionary signature

The artifact can carry an Ed25519 signature. `build-merchant-dictionary.ts` signs it when `data/dictionary.key` exists and writes `merchants.jsonl.gz.sig`. With no key it logs that the dictionary is unsigned, and a signing failure only warns.

At runtime `verify.ts` reads `DICTIONARY_PUBLIC_KEY` straight from `process.env`, so the variable skips the validated schema in `packages/env`. A blank or absent value means unconfigured, and the loader skips the check. With a key set, a failure never throws:

| Condition | Log line | Effect |
| --- | --- | --- |
| The `.sig` file is absent | `Dictionary signature missing: … - refusing to load` | The map stays empty |
| The signature does not check out | `Dictionary signature invalid: … - refusing to load` | The map stays empty |

A failure disables stage 3 and nothing else. Stages 1, 2, 4, 5 and 7 still run.

<Callout type="warn">

**The published artifact carries no signature, so a configured public key turns the dictionary off.** The weekly release tarball packs the dictionary and the place tokens. It sometimes packs the Wikidata brands and the weights, and never a `.sig` file. An instance that fetches its dictionary through `build:data` and sets a public key hits the missing-signature path. It loses stage 3 in silence.

`generate-signing-key.ts` prints a banner that names `verify.ts` as the place for the key. That file embeds no key and reads the environment variable alone. [Bank providers](/docs/self-hosting/bank-providers) holds the operator instructions for this trap.

</Callout>

## The classifier

`train-model.ts` trains a multinomial logistic regression over the 75 category slugs. One dense weight vector per category, plain stochastic gradient descent, L2 regularisation. Every hyperparameter is a literal:

| Name                       | Value           |
| -------------------------- | --------------- |
| `NUM_EPOCHS`               | `10`            |
| `LEARNING_RATE`            | `0.1`           |
| `L2_LAMBDA`                | `0.001`         |
| dimension                  | `65_536`        |
| `MIN_SAMPLES`              | `10`            |
| `HOLDOUT_FRACTION`         | `0.2`           |
| `SHUFFLE_SEED`             | `1_588_635_695` |
| `MIN_PRECISION`            | `0.75`          |
| `DICTIONARY_SAMPLE_WEIGHT` | `1`             |
| `CORRECTION_SAMPLE_WEIGHT` | `20`            |

Two sources feed it. The dictionary is a bootstrap prior at sample weight 1. Each entry with a resolvable category contributes its normalised name and every normalised alias. The database is the ground truth at sample weight 20. It contributes every `MerchantOverride` row, and every transaction with an override, a category and a normalised descriptor. The flag `--dictionary-only` turns the second source off.

Features come from `features.ts`. The helper `modelInput` folds the country into the input string. Then `extractFeatures` hashes character n-grams of length 3 to 5 with FNV-1a into 65 536 buckets. The output is `data/model-weights.json`, with the keys `categories`, `dimension`, `inputVersion` and `weights`. It holds one sparse bucket map per category. The runtime refuses any `INPUT_VERSION` other than `2`, and it refuses a schema mismatch.

### The shipping gate

The holdout splits **by merchant id**, so no alias of a training merchant reaches the evaluation. The trainer scores each held-out string once per inference country. **Each country slice is gated on its own, and the worst slice decides.** The rule is one comparison: that slice must reach `MIN_PRECISION`, measured at the accept threshold `0.7`.

| Exit code | Meaning | What the workflow asserts |
| --- | --- | --- |
| `0` | Trained and accepted | The weights file exists, and the run reports attached weights |
| `1` | The trainer failed, found no dictionary artifact, or found too few samples | The run fails |
| `2` | Evaluated and refused | The weights file must not exist, and the run reports a refusal |

Weights land on disk only after the gate passes. So the presence of stage 5 on an instance is conditional, and the code states the condition:

- The release tarball carries `model-weights.json` only when the trainer exited `0`.
- With no weights file, `loadModel` finds nothing and `predict` returns `null`. The pipeline then runs stages 1 to 4, and then stage 7.

That refusal is a designed outcome and not a break. A refused run leaves a deterministic pipeline.

## The weekly workflow

`.github/workflows/generate-data.yml` rebuilds the data and publishes a release.

| Field | Value |
| --- | --- |
| Schedule | `cron: "0 3 * * 1"`, so Monday at 03:00 UTC |
| Other triggers | `workflow_dispatch`, and a push to `dev` or `main` that touches `packages/api/scripts/**`, `features.ts`, `normalise/**` or `sirene/**` |
| Job timeout | 60 minutes |
| Permissions | `contents: write` |

The steps run in this order:

1. Install with `--ignore-scripts`.
2. Restore the SIRENE disk cache.
3. Run `generate-place-tokens.ts` and `fetch-wikidata-brands.ts` in parallel.
4. Build the dictionary.
5. Save the cache, in a separate step, so a cancelled run still publishes what it fetched.
6. Generate the Prisma client, which the install step skipped.
7. Train the classifier with `--dictionary-only`.
8. Pack the artifacts, then publish the release `data-<YYYY-MM-DD>` with the asset `merchant-data.tar.gz`.

The publish step deletes any same-day release and tag first, and it passes `--latest=false`. The train step reads `${PIPESTATUS[0]}` rather than `$?`. The default shell has no `pipefail`, and the command pipes through `tee`. The whole training log lands in the job summary.

A new slug needs no migration. A retired slug needs an entry in `LEGACY_CATEGORY_SLUGS` and a data migration over `transaction.category`, `transaction.resolvedCategory`, `merchant_override.category` and `budget_line.categorySlug`. The migration `20260831120000_category_hierarchy` is the worked example.

</Step>

</Steps>

<Callout type="warn">

**Two failure modes when the taxonomy and the catalogs disagree.**

`CATEGORY_MESSAGES` ends with `satisfies Record<SpendingCategory, () => string>`, so a slug with no entry is a TypeScript error. `apps/web` declares no `check-types` script, so `bun run check-types` misses that file.

A key in `en.json` with no twin in `fr.json` is worse. It compiles with no error and no warning. The French branch falls back to the English string, and no build step catches it.

</Callout>
