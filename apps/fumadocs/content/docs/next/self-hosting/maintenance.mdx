Run every command from the directory that holds `docker-compose.yml` and the `.env` file. Compose reads both from there. That directory needs no clone of the repository.

## Watch the disk

The database volume grows with the transaction history of your users. Nothing prunes it.

```bash
docker compose exec postgres du -sh /var/lib/postgresql
docker system df -v
```

The first command measures the database. The second lists every image, container and volume with its size. The database volume appears there as `freenary_freenary_postgres_data`.

Measure the largest tables when the volume surprises you:

```bash
docker compose exec -T postgres psql -U postgres -d freenary -c \
  "SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) FROM pg_catalog.pg_statio_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;"
```

The `transaction` table leads that list on a busy instance. A user who deletes a bank connection removes its accounts, transactions and holdings through the database cascade. That delete is the only shrink the product offers.

Container output is the second consumer of disk. Neither compose file sets a `logging:` driver, so the Docker default applies and the output is unbounded. Read [Logs](/docs/self-hosting/logs) for the cap.

## Prune old images

Each update leaves the image of the build before it without a tag.

```bash
docker image prune -f
```

The command deletes the untagged images. It keeps every image a container uses.

## Restart a service

```bash
docker compose restart server
```

A restart starts the same container again, so the container keeps the environment Compose gave it at creation. Use `up -d` instead after a change to `.env`:

```bash
docker compose up -d server
```

Compose reads the root `.env` file again, and it recreates each container whose configuration changed.

| Command | Reads a new `.env` value |
| --- | --- |
| `docker compose restart server` | No. The container keeps the environment of its creation |
| `docker compose up -d server` | Yes. Compose recreates the container |

## Stop and start the whole stack

```bash
docker compose down
docker compose up -d
```

<Callout type="error">

Never add `-v` to `docker compose down`. The flag deletes the named volume, and that volume holds the whole database.

</Callout>

## Check that the stack came back

```bash
docker compose ps -a
```

| What the `STATUS` column shows | What it means |
| --- | --- |
| `healthy` on `postgres`, `server` and `web` | The three long-lived services answer their healthchecks |
| `starting` | The service has not passed a healthcheck yet. The start period is 10 seconds |
| `unhealthy` | Five checks in a row failed. Read the log of that service |
| `Exited (0)` on `migrate` | The one-shot migration step finished. This is the healthy state |

The `-a` flag lists the exited `migrate` container. Plain `docker compose ps` hides it.

Then ask the two apps and the database directly:

```bash
curl -fsS http://localhost:3000/
curl -fsS -o /dev/null -w '%{http_code}\n' http://localhost:3001/
docker compose exec postgres pg_isready -U postgres -d freenary
```

The API server answers the plain string `OK`. The web app answers `200` with the rendered app. Point your own uptime checker at the same two requests.

## Open a database shell

```bash
docker compose exec postgres psql -U postgres -d freenary
```

## Read the migration state

```bash
docker compose exec -w /app/packages/db server bun x prisma migrate status
```

The command lists the migrations of the image and the ones the database holds. The `migrate` service applies the rest on every start. A manual `prisma migrate deploy` is a fallback, not a routine step.

## A schedule that keeps an instance recoverable

Freenary needs no fixed schedule. This one is enough.

| Task | How | How often |
| --- | --- | --- |
| Dump the database | [Backup and restore](/docs/self-hosting/backup-and-restore) | Daily |
| Read the service state | `docker compose ps -a` | Daily |
| Read the API server log | `docker compose logs --tail 100 server` | Weekly |
| Measure the volume | `docker compose exec postgres du -sh /var/lib/postgresql` | Monthly |
| Move to a newer tag | [Updates](/docs/self-hosting/updates) | Monthly |
| Prune old images | `docker image prune -f` | After each update |
| Prove a dump restores | [Backup and restore](/docs/self-hosting/backup-and-restore) | Twice a year |
| Rotate `BETTER_AUTH_SECRET` | [Security](/docs/self-hosting/security) | After a leak alone |

## What your own scheduler must carry

Freenary runs two web processes and one database. It holds no worker, no queue and no cron entry. Four jobs are yours.

| Job | How you do it |
| --- | --- |
| Take a backup | Put the dump command in your own scheduler |
| Cap the container output | Add a `logging:` block per service, as [Logs](/docs/self-hosting/logs) shows |
| Refresh a bank connection | A sync runs inside the request that asks for it. Tell your users to open the budget screen |
| Run any periodic job | Put it in your own scheduler on the host |
