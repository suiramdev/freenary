Run the code on your machine, pass the checks CI runs, and open a pull request against `dev`.

## Prerequisites

- **Bun.** The repository pins `bun@1.3.14` in `package.json`, and CI installs the latest Bun.
- **Node.js 20.19+, 22.12+ or 24+.** `bun install` runs Prisma's install script, which refuses other Node versions.
- **Docker with Compose v2.**

Then clone the repository and install:

```bash
git clone https://github.com/suiramdev/freenary.git
cd freenary
bun install
```

## Run it in Docker

```bash
bun run dev:up
```

It starts PostgreSQL, applies the migrations, and runs the API server, the web app and the documentation site with live reload. It prints the addresses it serves:

- `http://web.<slug>.freenary.localhost`
- `http://server.<slug>.freenary.localhost`
- `http://docs.<slug>.freenary.localhost`

The slug comes from your git branch, so two worktrees run side by side. A shared Traefik container on port 80 routes these hostnames. Use Chrome or Firefox, which resolve `*.localhost` on their own.

`bun run dev:logs` follows the logs, `bun run dev:down` stops everything, and `bun run dev:reset` deletes the database and starts over.

There's no seed data. Create an account on the sign-in screen: with no email provider, sign-up signs you in at once.

To work on emailed codes, start with `bun run dev:mail` instead. It adds a Mailpit inbox at `http://mail.<slug>.freenary.localhost`, and the server sends every email there.

### Bank data without credentials

When `.env` sets none of `BANKING_PROVIDER`, `POWENS_CLIENT_ID` and `ENABLE_BANKING_APP_ID`, `bun run dev:up` starts the server with `BANKING_PROVIDER=mock`, and prints `bank    mock provider, generated data`. The environment then owns `BANKING_PROVIDER`, so the setup screen can't pick another bank provider, and one saved there before is ignored. To use a real provider, set one of the three in `.env`.

The mock provider lists three made-up banks for every country. Connecting one opens a consent page on the API server: **Approve** returns to Freenary with a new connection, and **Decline** returns to Freenary as a refused consent. Each connection gets a checking account and a Livret A, and some also get a PEA or a life-insurance contract.

The checking account books French bank descriptors: card payments, direct debits, rent, a monthly salary and cash withdrawals. A day's transactions stay the same from one sync to the next, so a sync only adds the days since the last one. Today's card payments arrive as pending. Holdings take a new price every day.

## Run it without Docker for the apps

Only PostgreSQL runs in Docker:

```bash
cp .env.example .env
echo 'DATABASE_URL=postgresql://postgres:password@localhost:5432/freenary' > apps/server/.env
docker compose up -d --wait postgres
(cd packages/db && bun run db:migrate:deploy)
bun run dev
```

The server listens on port 3000, the web app on 3001 and the documentation site on 4000.

To use the mock bank provider on this path, add `BANKING_PROVIDER=mock` to `apps/server/.env`.

## Checks

CI runs `bun install --frozen-lockfile`, then these steps in order. Run them before you push:

```bash
bun run check         # Lint & format
bun run check-types   # Type check
bun run check:fsd     # Architecture
bun run docs:check    # Documentation
bun run env:check     # Environment
(cd packages/api && bun test)   # API tests
bun run build         # Build
```

`bun run fix` repairs most lint and format errors. A second CI job parses every Compose file.

On each commit, lefthook runs three jobs on the staged files:

- `oxlint --fix`, then stages the fixes.
- `oxfmt --write`, then stages the fixes.
- `bun run env:sync`, when the commit touches `packages/env/src/schema*.ts`, a `docker-compose*.yml` file or `scripts/env-sync.ts`.

## Tests

CI runs no tests, and there's no root `test` script. Run the files your change touches:

```bash
bun test packages/api/src/categorisation/dictionary.test.ts
```

## Pull requests

Open your pull request against `dev`. `main` holds released code. [`CONTRIBUTING.md`](https://github.com/suiramdev/freenary/blob/dev/.github/CONTRIBUTING.md) has the rules: branch names, the pull request template, signed-off commits, documentation in the same change.

The template's Evidence section is optional. For a change people can see, drag screenshots or a screen recording into it so GitHub hosts them. Use fake data only: no real keys, tokens or personal data, and no file paths from your machine. Reviewers check it on an interface change and ask for it when it's missing; no check fails without it. Delete the section when it doesn't apply, and say "no visual change" in Notes.

Maintainers cut releases from `main` with the `Release` workflow. Don't tag, and don't bump a version.

## Labels

Open an issue with the bug report, feature request or other form. Write the title plainly: the forms add no `[Bug]` or `[Feature]` prefix.

The tracker has twelve labels: `type: bug`, `type: feature`, `type: documentation` and `type: maintenance`; `priority: high`, `priority: medium` and `priority: low`; `impact: high`, `impact: medium` and `impact: low`; `good first issue` and `help wanted`. There are no status, area or signal labels.

The `Triage` workflow labels an issue or pull request with SubQ Snap (`subq-snap-1.1`) when it is opened or reopened. It runs again when someone edits the title or description, when the author replies, and when someone adds a `type:`, `impact:` or `priority:` label, `good first issue` or `help wanted`. On a pull request from a branch of this repository, it also runs when the `CI` workflow finishes. It skips closed items, skips a draft pull request until it is marked ready for review, and skips events a bot triggers.

It adds one `type:` label: the model's top answer whatever its confidence. An exact tie goes to the option listed first in `scripts/triage/questions.ts`. It adds an `impact:` label only when the model answers with a confidence of 0.8 or more, and an impact score halfway between two levels takes the higher one. It never guesses a priority. It derives one from the impact: `impact: high`, `impact: medium` and `impact: low` give `priority: high`, `priority: medium` and `priority: low`. A regression raises that priority one level, and a security risk gives `priority: high` with or without an impact. An `impact:` label already on the item replaces the model's impact. With no justified impact and no security risk, the item gets no priority and waits for a maintainer. The workflow recomputes a `priority:` label it set itself on each run, and removes it when a maintainer adds another `priority:` label. The run's summary and its `triage-record.json` artifact list each answer with its confidence and, when the model returns probabilities, the runner-up.

An issue can get `good first issue` when the model is at least 0.95 sure a newcomer could do it and nothing is missing from the issue. Neither `good first issue` nor `help wanted` goes on an issue whose `Still to define` section has an unchecked item: the workflow does not add them, removes them when someone else did, and asks a maintainer to settle the list. Once every item is checked, a maintainer can add `help wanted`, and the workflow can add `good first issue` again. The workflow never adds `help wanted` itself.

The model reads the title, the description and the author's replies. Readiness follows a checklist:

- A bug needs the steps that show it, what happened and what you expected, and the version or deployment.
- A feature needs the problem, the expected result, and no open design choice.
- A documentation issue needs the page and what is wrong on it.
- A maintenance issue needs what should change and why, and no open design choice.
- An issue with an unchecked item under `Still to define` waits for a maintainer.
- A pull request needs a written Summary, every section of the template filled except the optional Evidence, and passing `ci` and `compose` checks. When it changes documented behaviour and no page under `content/docs/next`, its Notes must name the pages or say why none needed a change.

When something is missing, the workflow posts one comment that lists it, for the author and for a maintainer, and names a possible duplicate. It updates that comment when the list changes. It deletes the comment once nothing is missing, when the item is blocked, when only a running check is left, or when a maintainer has set a `priority:` label. The workflow never replaces a group a maintainer already labelled, and never adds back a label someone else removed. It labels nothing when the repository has no `SUBQ_API_KEY` secret. A maintainer reruns it from the Actions tab with an item number.

`scripts/triage/taxonomy.ts` defines every label. The `Labels` workflow creates and updates them when that file changes on `dev` or `main`. It never deletes a label.
