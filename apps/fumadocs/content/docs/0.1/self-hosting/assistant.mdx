Freenary ships with no model. Name an endpoint and a model id, and the API server answers through them.

Name neither, and the API server answers nothing. A reader whose browser has WebGPU can still pick a model that runs on their own device.

## The variables

| Variable | Needed | Notes |
| --- | --- | --- |
| `AI_BASE_URL` | yes | The base URL of an OpenAI-compatible endpoint, with its version path |
| `AI_MODEL` | yes | The model id, exactly as the endpoint names it |
| `AI_API_KEY` | no | The key for that endpoint. A local runtime needs none |

`AI_BASE_URL` and `AI_MODEL` work as a pair.

With either one empty, the API server reports no model. The assistant route then refuses every request.

`AI_API_KEY` takes no part in that test.

`AI_BASE_URL` must parse as a URL. A bad value stops the API server at startup.

A hosted gateway takes all three variables:

```dotenv
AI_BASE_URL=https://openrouter.ai/api/v1
AI_API_KEY=sk-...
AI_MODEL=anthropic/claude-3.5-sonnet
```

A runtime on your own hardware takes two:

```dotenv
AI_BASE_URL=http://ollama:11434/v1
AI_MODEL=qwen2.5:14b
```

Give that runtime a service on the same Docker network, then name the service in the URL. The value `http://localhost:11434/v1` names the API server container itself, and it reaches nothing.

<Callout type="warn">

**The model must support tool calling.** The assistant reads the money data of a user through read-only lookups, and each lookup is a tool call.

A model without tool calling still answers. It answers about the money of the reader, it reads none of it, and it invents every figure. No error reports that.

Pick a model whose provider documents tool calling. Then ask one question that needs a figure, and check the answer before other people use the instance.

</Callout>

## What a reader sees with no model

The model button reads `Choose a model`. The text box, the send button and the three suggestion chips are all off.

One line sits above the text box. On a browser with WebGPU:

```text
Choose a model to start. It downloads once from Hugging Face, runs on your graphics card, and your questions stay in this browser.
```

On a browser without WebGPU:

```text
This browser has no WebGPU, which the assistant needs to run a model on this device. Use a current Chrome, Edge or Safari, or ask an administrator to set AI_BASE_URL and AI_MODEL.
```

A request that still reaches an unconfigured server surfaces one message:

```text
This instance has no model configured. An administrator sets AI_BASE_URL and AI_MODEL to switch the assistant on.
```

With both variables set, the model palette gains a group named `On your instance` that holds the id in `AI_MODEL`. That model answers by default.

[The assistant](/docs/guides/assistant) shows the whole screen from the side of the reader.

## The transport

The assistant does not use a procedure. It uses one route, `POST /ai/chat`, and that route streams its answer as server-sent events.

It refuses in a fixed order:

| Order | Status | Body | Cause |
| --- | --- | --- | --- |
| 1 | `401` | `unauthorized` | No session cookie |
| 2 | `503` | `unconfigured` | `AI_BASE_URL` or `AI_MODEL` is empty |
| 3 | `429` | `rate_limited` | The account is over its question limit |
| 4 | `400` | `bad_request` | The body is not JSON, fails the schema, or holds no user question |

The order matters. An unconfigured instance answers `unconfigured` even to a caller over the limit.

A question of more than 8000 characters is a `bad_request`. One question can drive up to 6 model steps, because each lookup and each retry is a step.

## What leaves the instance

A configured endpoint receives account data. Freenary posts to `<AI_BASE_URL>/chat/completions`, and each step of a question carries all of this:

| Part of the payload | What it holds |
| --- | --- |
| The system prompt | A statement that Freenary holds the bank accounts of the user, the locale, today's date, and the date of the first and the last transaction |
| The chart section of the prompt | The chart grammar and two worked examples |
| The transcript | Every stored question and answer of the active conversation |
| The tool signatures | The seven read-only lookups and their input schemas |
| Every tool result | The rows the lookups returned |

A tool result carries real account data:

- Account ids, account names and institution names.
- Per-group planned and actual amounts, cash-flow buckets, and fixed and variable totals.
- Recurring-payment merchant names, merchant keys and cadences.
- Individual transactions: the description, the counterparty name, the date, the id and the amount.

A transaction description and a counterparty name are the raw text the bank sent. They name the shops, the people and the companies the user paid.

**Freenary strips one field: the IBAN.** The accounts lookup drops it before the result leaves. No lookup takes an IBAN as an input either.

Amounts leave as decimal strings. Every lookup labels them `EUR`.

<Callout type="info">

A hosted gateway holds everything above, under its own terms. A runtime on your own hardware keeps all of it on your own host. That choice is the whole difference between the two `AI_BASE_URL` examples above.

</Callout>

<Callout type="info">

With `AI_BASE_URL` unset, the API server makes no outbound call for the assistant at all. The browser of the reader still makes two. The model weights come from `https://huggingface.co`. The compiled model library comes from `https://raw.githubusercontent.com`.

An egress allow-list must hold both hosts for a device model to load.

</Callout>

## The browser model

A reader whose browser has WebGPU can run the assistant on their own device. The model comes from [WebLLM](https://github.com/mlc-ai/web-llm).

You set no variable for it, and you cannot switch it off.

| Concern | What a device model means for you |
| --- | --- |
| Your work | None. You set no variable, and you install no runtime |
| What the reader needs | WebGPU, and enough graphics memory for the model |
| Outbound traffic | The one-time model download, from the browser of the reader |
| Load on the instance | The lookups alone. No model call reaches the API server |
| The rate limit | The same 30 stored turns per 300 seconds |
| The transcript | The browser stores each finished turn in the same tables |
| Answer quality | Lower. A model that fits in a browser is small |

With `AI_BASE_URL` and `AI_MODEL` set, the palette holds both kinds. The instance model answers by default. A device model the reader picked wins over it.

## The rate limit

One account gets **30 server calls per 300 seconds**. One allowance covers both kinds of answer: a question the instance model answers, and a turn a device model produced. The code fixes that limit, and no variable changes it.

The key is the account id, not the caller address. Each question is a call to your model endpoint, so the cost follows the account that asks. One busy office behind one address keeps a full allowance per person.

Over the limit, the route answers `429` and the screen asks the user to wait.

A device model runs in the browser, so it needs no allowance to answer. The procedure that stores the finished turn does, and it shares the key. Over the limit, the answer stays on the screen and Freenary stores no turn.

## Where the conversation lives

Every question and answer goes into PostgreSQL, never into process memory. So a restart keeps a conversation, and a second replica reads the same rows.

An account holds one active conversation. The `New conversation` control archives the current thread and opens an empty one, and no picker returns to the old one.

Freenary drops those rows with the account they belong to. The tables grow with use, so they belong in your backup plan.

## Cost

Each question is one call to your model endpoint, and a question with lookups is several. Nothing on the instance caches an answer.

So the cost of the assistant follows how many questions your readers ask, and how large each transcript grows. The 30-per-300-seconds limit is a ceiling per account, not a budget.

A device model costs the instance no model call. It still runs the lookups against the API server and the database.
